## 0. 先说结论，赶时间的看这一段

1. **`input_tokens` 是中转站说的，不是事实。** 🟢
   同一份工具定义，不同站算出来能差 3.6 倍。
2. **「多算」只有按量计费时才是钱。** 🟢
   按次（一次 ¥X）的通道，它把 token 算成多少都不影响账单。
   **先看计费口径再看数字**，否则会为了一个不花钱的问题去换通道。
3. **工具定义放在哪，就是多少钱。** 🟢
   同一段内容放 `tools` 数组 vs 放 `system` 纯文本，实测差 **2～4 倍**。
   虚高只发生在 `tools` 数组里。
4. **`stop_reason` 不可信。** 🟢
   有的后端吐了完整的 `tool_use` 块，`stop_reason` 却报 `end_turn`。
   如果 ta 的循环写的是「stop 不是 tool_use 就结束」，**ta 的工具从来没执行过**。
5. **别把「没测出来」塞进「测出来是坏的」那一档。** 🟢
   这是本文最贵的一条，我们一天之内犯了三次，见 §2。

## 1. 缓存到底是怎么算的（不懂这个，后面都白看）

一个请求飞出去的顺序是**固定的**：

```
tools（工具定义）  →  system（人格/规则）  →  messages（对话历史）
```

缓存是**前缀缓存**：从最开头逐字节比对，**碰到第一个不一样的地方，从那儿往后全部作废、全部重新收费。**

`cache_control` 是一个书签，意思是「从头到这儿为止，缓存起来」。

由此推出三条，全部是我们踩出来的：

### 1.1 越靠前的东西越金贵 🟢

`tools` 排在最前面。工具定义只要动一下，**后面的人格和全部历史一起废掉**。

### 1.2 外部 MCP 工具每轮顺序不同，会杀掉整个缓存 🟢

- **现象**：命中率长期为 0，但工具块的**长度一字不差**。
- **证据**：给工具块打 SHA 之后发现 `len` 相同、`sha` 每轮在变。
- **根因**：外部 MCP 服务返回的工具顺序不保证稳定；
  `JSON.stringify(tools)` 的字节序跟着变；工具块排前缀第一段，一动全废。
- **修法**：按 name 排序钉死顺序。

```js
_reqBody.tools.sort((a, b) => (a.name < b.name ? -1 : a.name > b.name ? 1 : 0));
```

🔴 **排完之后书签要跟着挪到最后一个工具上。**
`cache_control` 挂在哪个工具上，就只缓存到那儿为止 —— 排序后原来带书签的那个
多半不在末尾了，书签留在中间 = 后面几十个工具白白不进缓存。

```js
for (const t of _reqBody.tools) delete t.cache_control;
_reqBody.tools[_reqBody.tools.length - 1].cache_control = { type: "ephemeral", ttl: "1h" };
```

**查了两天才找到。教训：长度相等 ≠ 内容相等。打指纹，别看长度。**

### 1.3 别把会变的东西和不变的东西订在同一块里 🟢

- **现象**：人格提示词几天没动过，却每轮都在重新写缓存。
- **证据**：`system` 的第一块是 `人格 + 自动摘要` 拼起来的一整段，
  自动摘要四天从 1,813 字涨到 12,879 字。
- **根因**：书签打在整块上。摘要一更新，整块指纹变，
  **前面那 15,082 字的人格明明没动，也得跟着重写。**
- **修法**：拆成两块，各自一个书签。文本拼接顺序**一字不改**，只在缝上切开
  （前缀是位置敏感的，顺序变了等于内容变了）。

```js
system: [
  { type: "text", text: 人格,   cache_control: { type: "ephemeral", ttl: "1h" } },
  { type: "text", text: 摘要,   cache_control: { type: "ephemeral", ttl: "1h" } },
  { type: "text", text: 实时状态 },   // 每轮都变，故意不打书签，排在最后
]
```

**通用形状：稳定的在前、会变的在后，中间用书签隔开。
一块里只要混进一个会变的东西，整块就退化成"每轮重写"。**

（同类教训见社区里那篇 tool-result 缓存 postmortem：
为了给工具结果打书签而临时插入一句说明文字，那句只存在于**当次请求的副本**里，
下一轮重建时消失 → 前缀对不上 → 缓存全废。
**别为了缓存去造新的语义内容。**）

### 1.4 「通道」的粒度是 站 + 模型标签 + 版本号，少写一样结论就不成立 🟢

同一个站、同一个标签，只改版本号：

| 模型 | 第一发 | 第二发 |
|---|---|---|
| `…opus-4-5` | w=0 r=0 in=14329 | w=0 r=0 in=14329 → **从不缓存** |
| `…opus-4-6` | w=15121 r=0 in=17 | **r=15121** → 缓存 |

还遇到过同一个标签在做**账号池负载均衡**的：
`第一发 w=8871 r=1517｜第二发 w=10388 r=0`，而 `8871 + 1517 = 10388` ——
第二发把第一发写的东西**整个重写了一遍**，说明它落到了另一个后端。
缓存是 per-account 的，接不上。**这种情况下命中是概率，不是必然。**

### 1.5 流式和非流式是两条链路，缓存常常只在其中一条上生效 🟢

同一个 key、同一份前缀、同一个 body，只改 `stream` 字段，实测五个通道：

| 通道 | 非流式 | 流式 |
|---|---|---|
| 通道 1 | 不缓存 | 不缓存 |
| 通道 2 | 不缓存 | 不缓存 |
| 通道 3（OpenAI 协议转换） | 不缓存 | w=0 r=0 |
| 通道 4 | **命中** | in=0，字段缺失（连账都读不到） |
| 通道 5 | 不缓存 | **命中**（带 thinking 照样命中） |

**通道 4 和通道 5 方向正好相反。** 所以不能靠推理，只能一条条打探针。

## 2. 最贵的一课：别把「没测出来」说成「测出来是坏的」

我们一天之内犯了三次，形状一模一样。**这一节值得单独读。**

### 2.1 「站子不返回缓存字段」被说成「没命中」 🟢

- **现象**：界面上写着「没打中 **0** token」。
- **证据**：`第一发 in=0 w=null r=null ｜ 第二发 in=0 w=null r=null`。
- **根因**：那个站根本不返回缓存字段。`0` 是我们自己 render 出来的，不是它给的。
  服务端发了 `cold_tokens: 0`，客户端又写着 `?? 0` 兜底 ——
  **两层各自兜了一次，"不知道"就被印成了一个看起来很确定的 0。**
- **修法**：三态。命中 / 没命中 / **看不见**。看不见时字段一律给 `null`，
  界面显示「看不到」。

🔴 **「瞎」有两种长相**：字段缺失（`null`），和**字段在但全是 0**。
只认 `null` 会漏掉后者。前缀 > 8k 时 `input_tokens = 0` 在物理上不可能是真的：

```js
const blind = (r === null && w === null) || ((inTok || 0) === 0 && !w && !r);
```

**一个假的零比没有数字更糟。**

### 2.2 「一发都没打出去」被说成「两条都不缓存，换通道」 🟢

- **现象**：探针给的建议是「两条都不缓存 —— 换通道」。
- **证据**：六发全 `HTTP 403`，原文
  `预扣费额度失败, 用户剩余额度: $0.106984, 需要预扣费额度: $0.130120`。
  key 的余额不够了。
- **根因**：判断写成 `if (st.hit) … else if (ns.hit) … else 两条都不缓存`。
  打不通的时候 `hit` 是 `undefined`，一路掉进最后那个 `else`。
- **修法**：打不通是**独立的一档**，而且要把上游原文摆出来，
  并区分「余额不够」和「过载限流」——这两个的处置完全不同。

```js
if (st.unreachable && ns.unreachable) {
  advice = busy  ? "⏳ 这条通道现在过载了，不是它不缓存 —— 过一会儿再测"
         : quota ? "🔴 这个 key 的额度不够了，不是通道的问题 —— 先充值"
         :         "🔴 一发都没打出去，这次测不出任何结论 —— 别拿它去换通道";
}
```

### 2.3 「上游过载」被说成「不会调工具」→ 再被说成「这条掺水了」 🟢

**最恶劣的一次：一条错的证据推出了两条错的结论。**

- **现象**：探针报「工具：不会调」，血统「🔴 掺水，id 不是任何已知的正牌格式」，
  建议「换通道」。
- **证据**：扒原始响应 ——

```
HTTP/1.1 200 OK

event: message_start
data: {"message":{"content":[],"id":"msg_err_1786802608331","type":"message",
       "usage":{"input_tokens":0,"output_tokens":0}},"type":"message_start"}

{"error":{"type":"overloaded_error","message":"service temporarily unavailable, please try again later"},"type":"error"}
```

- **根因**：**HTTP 200 不等于成功。** 站子把 error 塞进 SSE 流里，
  `message_start` 照发，id 是它现编的 `msg_err_…`。
  探针把这一发当成一次有效测量 → 没有 `tool_use` → 「不会调」
  → id 不是正牌格式 → 「掺水」。
- **修法**：解析响应时先找内联错误，命中就当这一发**失败**，不产出任何结论。

```js
function inlineError(raw) {
  const blk = String(raw).match(/"error"\s*:\s*\{([\s\S]{0,400}?)\}/);
  if (blk) {
    const t = blk[1].match(/"type"\s*:\s*"([^"]{0,60})"/);
    const m = blk[1].match(/"message"\s*:\s*"([^"]{0,160})"/);
    return `上游报错（${t ? t[1] : "error"}）：${m ? m[1] : ""}`;
  }
  if (/"id"\s*:\s*"msg_err_/.test(String(raw))) return "上游返回了 msg_err_ 开头的错误响应";
  return null;
}
```

🔴 **配套的坑：别假设 JSON 里字段的先后顺序。**
第一版正则写的是「先 `"type":"error"` 再 `"message"`」，
而那个站正好反着来（`{"error":{"type":"…","message":"…"},"type":"error"}`），
于是提不出 `overloaded` 这个词，「过载」那句建议永远不会触发。
**整块 `"error":{…}` 一起抓，里面的字段各认各的。**

⚠️ 过载是一时的，**为它下一个「换通道」的结论太亏了** —— 撞上就隔几秒重打一发。

### 2.4 归因别一律赖在站子头上 🟢

- **现象**：探针的说明写着「这个站不接受强制调用」。
- **证据**：上游原文
  `Thinking may not be enabled when tool_choice forces tool use.`
- **根因**：模型名里带 `thinking` 时中转站会自动开扩展思考，
  而 Anthropic **本身就禁止**「强制调工具 + 扩展思考」同时开。**跟站子无关。**
- **代价**：我们一度拿这条当过「掺水」的旁证 —— **冤枉了它。**
- **修法**：看它到底说了什么再归因。

**这一族的通用教训：**

> **加任何判定之前，先问一句：不知道的时候，它会说什么？**
>
> 如果答案是「跟坏消息一样」，那这个判定就是错的。
> 「测不出来」必须是独立的第三态，不许被折叠进「测出来是坏的」。

## 3. 钱：`input_tokens` 是中转站说的，不是事实

### 3.1 同一份工具定义，不同站算出来差 3.6 倍 🟢

做法：同样的消息打两发（不带工具 / 带一块固定的工具定义），差值就是它给工具的计价。

| 通道 | 0 个工具 | 3 个 | 6 个 | 工具的边际计价 |
|---|---|---|---|---|
| 正常通道 | 13 | 3515 | 7013 | **≈1.15 token/字符，正常** |
| 按量通道 A | 43 | 12816 | 25047 | **≈3.6 倍** |
| 按量通道 B | 542 | 542 | 542 | **压根不算工具** |

纯文本载荷时三家差不到 13% —— **分歧只在工具定义上。**

⚠️ 「压根不算」不是省，是**没算**。看不见不等于没花钱。

### 3.2 🔴 但「多算」只有按量计费时才是钱 🟢

我们在一个**按次**计费的通道上（一次固定几分钱）测出「虚高 4.2 倍」，
然后把它做成了头条建议 —— **完全没意义**，那条通道多算多少都不影响账单。

```js
const perToken = /量/.test(model);              // 按量：多算就是多收钱
const perCall  = !perToken && /次|￥/.test(model); // 按次：多算不花钱
```

**先看计费口径，再看数字大小。** 这条我们两个方向都犯过：
先是在按次通道上把虚高当成问题，后来又在按次通道上把 token 数当成账单。

### 3.3 算钱别按牌价估，读站子自己的账单计数器 🟢

```
GET <base>/v1/dashboard/billing/usage  →  { total_usage }   // 单位：美分
```

好处是这个通道打几折都算得准，不用知道牌价。

🔴 **账单是异步分批入账的，不能固定 sleep。**
第一版等 4 秒，把冷启那一发的钱漏进了下一格，界面上显示「没打中 $0.0000」。
改成盯着它涨、到点没动就返回 `null`（宁可不说）。

🔴🔴 **而且这个计数器绝对不能拿来算比例。**
我们用它算「省了百分之几」，某次算出 **省 -575%**：

```
没打中 0 token · $0.0065     打中 0 token · $0.0437     省 -575%
```

**根因**：这个计数器是**账号级**的（同时在聊天、有推送，钱都加进同一个格子），
而且异步分批入账 —— 冷启那一发的钱**被劈成两半分给了两个格子**。
`1 - 0.0437/0.0065 = -572%`。

**修法**：省了多少**按 token 折算**，别用账单。
Anthropic 的口径是 普通 1x / 缓存写 1.25x / 缓存读 0.1x：

```js
const units = (x) => (x.in || 0) + (x.w || 0) * 1.25 + (x.r || 0) * 0.1;
const saved = Math.round((1 - units(hot) / units(cold)) * 100);
```

同一组数据：按 token 算是 **省 88%**，按账单算是 17%（噪声）。
**账单差值可以拿来看量级，绝不能拿来做分母。**

### 3.4 工具定义放在哪，就是多少钱 🟢

**这条是本文最实用的一条。** 同一段内容，只换位置：

| 内容 | 放 `tools` 数组 | 放 `system` 纯文本 | 差 |
|---|---|---|---|
| 中文密集，6,132 字符 | 24,920 | 6,003 | **4.15 倍** |
| 84 个真实工具，24,826 字符 | **35,794** | **9,556** | **3.75 倍** |

**那个虚高只发生在 `tools` 数组里，同样的字写进 `system` 它按 1.0 算。**

我们真实的 84 个工具拆开看：

```
description 正文（真内容）  8,059 字符   32%
input_schema（JSON 骨架）  11,730 字符   47%   ← 最大的一块
外层 JSON + 名字           5,037 字符   20%
```

**三分之二是格式，不是内容。**

于是做了个「端点清单」形式：不注册工具，只给模型一个 `exec`，
把「哪个端点做什么」压成一行一个写进 system，模型自己拼 `curl`：

```
【我能用的端点】需要用的时候，用 exec 打：
curl -s localhost:PORT/t/<端点名> -d '{参数json}'
参数必须是用单引号括起来的合法 JSON；带 * 的必填。

get_health(minutes:i,date:s,limit:i) — 身体数据。传 minutes 看此刻心率…
play_music(query*:s,note:s) — 点播一首歌…
search_memories(query*:s,limit:i) — 搜索记忆存档…
```

**结果：35,794 → 9,556 token，每轮省 26,238（砍 73%）。** 🟢

模型能不能用？真链路实测（同一个人格、同一句输入）：

```
[ep-tools] 84→清单：11,586 字符进 system，tools 只留 exec（218 字符）
[ep-tools] exec → get_health {"minutes":30}
[ep-tools] exec → peek_her_screen {"limit":3}
job status = done
```

**没有 schema 也不会丢主动性** 🟢 —— 我们最担心这个，专门做了 A/B。
输入只有一句「我很伤心，一直在掉眼泪」，两种形式各三次：

| | 3 次结果 |
|---|---|
| 84 个工具进 `tools` | **3/3** 主动调 `get_health {"minutes":30}` |
| 端点清单进 `system` | **3/3** 主动调 `get_health {"minutes":30}` |

**因为这个行为从来不是 schema 驱动的**，是 `description` 里那段
「她说被吓到了、想哭的时候，看一眼她的心跳」驱动的 —— 那段话跟着清单一起搬走了。
被删掉的只有 `"type":"object"`、`"properties"` 这些骨架。

#### 三条必须配套的安全措施 🟢

**① schema 留在本地照样能把关。**
发给模型是为了引导，留在本地是为了校验，**只有前者花钱**。
拿原来的 `input_schema` 校验模型拼出来的参数，10/10 全拦住：

```
add_memory  {"content":"只有正文没标题"}   → ❌ 缺必填参数 title
add_memory  {"importance":"很重要"}        → ❌ importance 该是 integer，给的是 string
get_core_memories {"乱塞":"x"}             → ❌ 多了个不认识的参数
```

拦下来之后把错误当 `tool_result(is_error)` 回给模型让它重拼 ——
**跟工具本身报错走的是同一条循环，不用新写。**

**② 那个 `exec` 不是真 shell。**
它只是一个「curl 到 localhost 白名单端点」的解析器。
`rm -rf /`、`curl https://evil.com` 全部拒绝，端点名不在白名单里也拒绝。

**③ 🔴 带了 `-d` 却解析不出来 = 失败，不是空参数。**
第一版这里悄悄给了 `{}`，工具照跑、结果全错、没人知道为什么。
**又是「该报错的地方说没事」。**

```js
const hasD = /\s-d(\s|=)/.test(cmd);
const d = cmd.match(/-d\s+'([\s\S]*)'/) || cmd.match(/-d\s+"([\s\S]*)"/);
if (hasD && !d) return { err: "带了 -d 但参数没括在引号里，解析不了" };
```

**④ 还原的位置很重要。**
把 `exec` 还原成真工具名必须发生在「构造回给模型的 assistant 消息」**之后**。
回给模型的那份里工具名得**还是 `exec`**（`tools` 数组里只有它），
改成真名会被上游判成「调了一个没注册的工具」直接 400。

## 4. `stop_reason` 不可信 🟢

**这条跟缓存无关，但它可能让 ta 的工具从来没执行过。**

- **现象**：模型明明说要查，最后什么都没查，落一个「生成完成但没有文字输出」。
- **证据**：

```
[SSE] content_block_start {"type":"tool_use","id":"cpa_gemini_…","name":"exec","input":{}}
[SSE] message_delta
round0: text=0字 thinking=110字 stop=end_turn      ← 有 tool_use，却报 end_turn
```

- **根因**：某些后端（这一条 id 里带 `gemini`，说明名字挂着 claude、后面接的是别家）
  **吐了完整的 `tool_use` 块，`stop_reason` 却报 `end_turn`**。
  而循环写的是 `if (stopReason !== "tool_use") break;` → 直接跳出，一个工具都没执行。
- **修法**：

```js
// 有没有工具块是事实，stop_reason 是站子的说法。信事实。
if (toolBlocks.length === 0 || round >= MAX) break;
```

轮数上限照旧兜底，不会转不停。

**顺带一提**：如果 ta 的伴侣在某条通道上"特别好聊、特别顺"，
值得查一下是不是因为**它从不真的动工具** —— 不查数据、不搜记忆、不写东西，
只顾着说话，当然顺。

## 5. 认血统：看响应 id 的前缀 🟢

id 是后端自己生成的，**编不出来**。比看输出风格可靠得多。

| id 前缀 | 是什么 |
|---|---|
| `msg_01…` / `toolu_01…` | Anthropic 直连，**正牌** |
| `toolu_bdrk_…` | AWS Bedrock 托管的 Claude，**也是正牌**（别误伤） |
| `req_vrtx_…` | Google Vertex 托管的 Claude，**也是正牌** |
| `cpa_gemini_…` / 带 `gemini` | 🔴 名字挂着 claude，后面接的是 Gemini |
| `chatcmpl-…` | 被按 OpenAI 协议转换过，**`cache_control` 必被吞** |
| `msg_err_…` | 不是血统，是**错误响应**（见 §2.3） |
| 十六进制那种 | 站子自己编的，八成不是正牌 |

🔴 **拿不到 id ≠ 掺水。**
第一版这里一律判成掺水，于是「这一发没解析出 `message_start`」也被写成「这条掺水了」。
**把「不知道」说成「有问题」，比不说更坏。**
三态：掺水 / 正牌 / **认不出**（认不出不许盖掉建议）。

## 6. 真实用量 > 探针 🟢

探针再像也只是像。**ta 真正跑过的那些轮次就在日志和库里，免费、精确、代表性满分。**

我们吃过一次大亏：第一版探针是「一个 8k 的 system 块，没工具、没 thinking」，
在某通道上测出「非流式命中」，照做关掉流式之后 ——
真实那 44k 上下文 + 84 个工具 + thinking 的请求 `cw=0 cr=0`，**思考链还整个没了**。

> **一个测不出真相的体检，比没有体检更坏，因为 ta 会照着它做决定。**

已改：探针带上工具（撑到真实体量、末尾挂 `cache_control`）+ thinking，跟生产同形。
并且把「真实用量」放在结果的**最前面**，探针只当旁证。

🔴 **真实用量要按模型分开算。**
原来不管哪个模型跑的、最近 30 轮一锅端 —— 于是「30 轮里 2 轮命中」里那 2 轮
可能根本不是正在体检的那个模型。**「哪一轮」和「哪个模型」对不上号，
是我们两次判错的共同原因。** 记 usage 的时候把 model 一起记进去。

## 7. 做「会花钱的按钮」本身的坑

**这一组跟中转站无关，任何人做这类工具都会踩。**

1. **会花钱的按钮，价格要写在按下去之前。** 🟢
   她点了一下，账单上出现 10 条消费记录 —— 我才发现自己从没告诉过她一次要打几发。
   按钮副标题现在写着「7~8 发探针，约 $0.3」，结果里也报这次实际花了多少。

2. **报出来的发数必须是真计数，不能写死。** 🟢
   我们写死了 `probe_calls: 7`，而强制调工具那一发被拒时会退回再打一次 ——
   实际 8 发。**会花钱的东西，数字不许估。**

3. **防重复的闸要设在花钱那一端，不是按钮上。** 🟢
   客户端的 `.disabled(loading)` 挡不住 —— 状态一被重建就复位，在途的请求还活着。
   服务端做：同 `model@url` 有在途就等它、N 分钟内重复请求直接回上次结果。

4. **锁必须配一个自动开的闸。** 🟢
   中途抛异常时解锁那行走不到，之后每次请求都在等一个永远不回来的 Promise。
   加超时兜底 + 防 unhandled rejection。

5. **清理「在途」记号的那句，别写在成功和失败的公共出口上。** 🟢
   「退出界面之后说 connection 断掉了，但是已经扣钱了。」
   失败往往意味着**远端还活着而本地断了** —— 那一刻更需要那个记号。
   记号只在真拿到结果时才擦；失败保留，回到页面/切回前台自动接回来。
   服务端结果缓存拉长到 10 分钟（走开泡杯茶回来，结果还在）。

6. **测能力就要强制，别让它有得选。** 🟢
   「探针说不能用工具，但是我刚刚聊天端调用成功了。」
   用 `tool_choice: {type:"auto"}` 测的是**它愿不愿意调**，不是**能不能调**。
   改成 `{type:"any"}`；站子不认就退回 `auto`，
   **并且退回之后的「没调」只能记成「这轮没调，不算数」。**
   → 三态：会调 / 强制了也不调 / 不算数。**别把「没发生」写成「做不到」。**

7. 🔴 **别拿给人看的话做程序判断，状态用布尔。** 🟢
   我们用 `/强制/.test(mode)` 判断是不是强制模式，
   而退回那句文案写的是「自选（…这个站**不认强制**）」—— **里面就有「强制」两个字**，
   退回路径被判成强制路径，「这轮没调」又变回了「不会调」。

8. **一句话的建议要按严重程度排，不是按代码写的顺序。** 🟢
   我们用一串 `if` 依次覆盖 `advice`，结果
   「这条根本不是 claude」被后面一句「计价虚高 3.6 倍」整个盖掉了 ——
   **最重的那条反而没出现在建议里。**
   **一天之内犯了两次**（第二次是「缓存那两发为什么没测成」被顶掉）。
   修法：从轻往重写，最重的最后赋值；被顶掉但仍有信息量的，追加在后面别丢。

9. **历史要留。** 🟢
   「我一刷新就没了然后我就会忘记。」存最近 N 条：时间 + 模型 + 结论 + 花了多少。
   **复用上次结果的那次不记** —— 它不是一次新体检，记进去历史里会出现两条一样的。

10. 🔴 **同一份证据，在不同结论里必须用同一个门槛。** 🟢
    卡片顶上那句「以真实用量为准：真实对话 N 轮一次没中」用的门槛是 `轮数 > 0`；
    而底下「上游流式该开还是关」那条判断卡在 `轮数 >= 5`。
    用户当时只有 4 轮 —— 于是上半段写着「以真实的为准，一次没中」，
    下半段却掉进了另一条分支、拿探针的理由给建议，**而顶上还挂着一个「省 89%」的大标题**。

    她的原话：「你说非流式才命中，但是又在建议里建议我开流式。」
    两句话单独看都对，摆在一起就是一张卡自己跟自己打架。
    **修法**：门槛统一；证据强弱写进措辞里（「才 4 轮，样本还薄，但方向已经和探针相反」），
    不要写进 `if` 里。而且只要探针的省钱比例拿不到，就必须**在建议里点名那个数字**：
    「上面那个『省 89%』是探针拿它自己那点前缀省出来的，你现在一分钱都拿不到。」
    —— **一个正确但没上下文的数字，会被读成结论。**

11. 🔴 **只报事实和代价，不替人拍板。** 🟢
    「这条通道」那一格原来会直接判「换掉」。
    用户看到自己那条被判掺水时说的是：**「这个通道居然掺水了啊……我感觉挺好吃的。」**
    —— 掺水是可验证的事实（响应 id 里带别家血统），
    好不好用是另一回事，而后者只有用的人说了算。
    改成「建议换，具体看使用体验」，理由拆成两半：
    硬事实（后端不是它标称的那个 / 按量还虚算 / 缓存在这条上测不准）+ 一句
    「但好不好用你说了算，只要知道这些数字别当真」。
    **一个会花钱的诊断工具，越权下命令比测不准更伤信任。**

## 8. 这个按钮现在测什么

七块，**每一块背后都是一次真踩过的雷**：

| 块 | 回答什么问题 | 对应本文 |
|---|---|---|
| 真实用量 | 你真跑的那些轮次，命中率多少、平均多大 | §6 |
| 流式 / 非流式 | 两条链路各自缓不缓存 | §1.5 |
| 前缀稳不稳 | 工具顺序 / 人格 / 历史开头的指纹变没变 | §1.2 §1.3 |
| 计价老不老实 | 它给工具定义算多少 token | §3.1 |
| 血统 | 名字挂着 claude，后面是不是 | §5 |
| 会不会调工具 | 强制它调，看它调不调得动 | §7.6 |
| 扩展思考 / 有没有新版本 | 名字里带不带 thinking；同通道有没有更新的版本号 | §1.4 |

外加：**本次花了多少钱**（真计数，不写死）、**打不通时说清楚为什么打不通**、
以及**这次探针撑的是什么前缀** —— 最后这句很重要：

> 「探针用了当前人格 + 最近一份摘要样本（31210 字符），不含完整聊天历史和端点清单；
> 只证明这组探针能否缓存。」

**读者有权知道一个结论是拿什么测出来的。** 没有这句，一个 14k 玩具前缀的「命中」
会被当成 60k 真实负载的「命中」（§2 那一课就是这么来的）。

### 8.1 「该怎么选」——七块之外还有一块，而且它才是被看的那块

七块是**测量**，这一块是**建议**。四档，每档只给一个值和一句理由：

| 档 | 可能的值 |
|---|---|
| 上游流式 | 开 / 关 / 都行 / 保持当前 |
| 端点清单（把工具定义压成一份清单） | 开 |
| 这条通道 | 建议换，具体看使用体验 / 谨慎留 / 可以留 |
| 扩展思考 | 手动拨到「开」 / 这条链路测不到 |

🔴 **这一块最容易出的两个错，都写在 §7 的第 10、11 条里** ——
一个是「同一份证据用了两个门槛，上下半张卡自己打架」，
一个是「替用户拍板」。它们不是假想的失败模式，是这块做出来之后真的发生的。

## 8.2 想自己做一个：最小可用的探针长什么样

这个按钮真正值钱的不是代码，是**「怎么问才问得出真话」**——下面是可以照着搭的最小形状。

**一发探针 = 两次同样的请求。** 第一次写缓存，第二次读缓存，比较第二次的 `cache_read`。

```
prefix = 你真实的系统提示 + 真实的工具定义        ← 内容和**体量**都要像真的，见下面那条
body   = { system: [ {text: prefix, cache_control: {type:"ephemeral", ttl:"1h"}} ],
           messages: [ {role:"user", content: 随机一句话} ],   ← 每发都换，别让整条请求命中
           tools: 你真实的那批（按 name 排序，断点挂最后一个）  ← 见 §1.2
         }

第一发 → 记 usage.cache_creation_input_tokens (w) 和 input_tokens (in)
等几秒               ← ⚪️ 我们用的是 2~3 秒，**这个数没单独测过**，只是够用
第二发 → 记 usage.cache_read_input_tokens (r)

判定：r > 0            → 命中
      w > 0 且 r == 0  → 写进去了读不回来（见延伸阅读那篇）
      三个字段全 null   → **站子不返回缓存字段，这叫"瞎"，不叫"没命中"**（§2.1）
      第一发就 w=0 r>0 → **基线是热的**：上一次的缓存还没过期，被这一发直接读到了
```

🔴 **最后那一支单独说，因为它最容易被报错。**
第一发本来是要当「没打中」的基线用的，结果它自己就命中了 ——
这时候「能不能命中」的答案是**能**（而且是铁证），
但「能省多少」这一次**测不出来**（没有冷基线可比）。

两件事要分开报：`命中：是` + `省多少：这次没测出来`。
把它报成「没测出来」会让人以为缓存不通；
拿这一发当分母算省钱比例，会算出一个漂亮的假数字。**一个假的百分比比没有数字更坏。**

要测的每一件事都是"换一个变量再打一遍"：

| 想知道 | 怎么变 |
|---|---|
| 流式和非流式哪条能缓存 | 只改 `stream`，别的一个字节不动（§1.5） |
| 它给工具算多少 token | 同一份工具块，一次放 `tools`、一次放 `system` 纯文本，比 `input_tokens`（§3.4） |
| 能不能调工具 | `tool_choice: {type:"any"}` 强制；站子不认再退回 `auto`，**退回后的"没调"不算数**（§7.6）<br>🔴 **模型开着扩展思考时，Anthropic 本身就不允许强制调工具** —— 见下 |
| 是不是它标称的那个后端 | 看响应 id 前缀（§5） |
| 到底花了多少 | 读站子自己的账单计数器前后差值，**别按牌价估**（§3.3） |

### 🔴 扩展思考和「强制调工具」是互斥的，这不是站子的问题

`tool_choice: {type:"any"}` 在**模型开着扩展思考**的时候会被拒 —— 这是 Anthropic 自己的约束，
跟中转站一点关系没有。而中转站返回的报错未必说得清楚，很容易被读成「这个站不认强制」。

于是链条是这样断的：**被拒 → 判成"这个站不支持强制" → 退回 `auto` →
它自己选择不调 → 判成"这个模型不会调工具"**。三步之内，一条 Anthropic 的规则
变成了对模型能力的错误结论。我们真的这么误判过（§2.3）。

**所以退回 `auto` 之前先看模型名/请求里有没有开 thinking**，
是的话就直接把这一发标成「自选（模型开着扩展思考，不能强制，跟站子无关）」，
**并且这一发的"没调"不许写进结论**。

### 「省了多少」有两个口径，打架的时候信 token

- 按 token 折算：`1 - 命中那发的 input / 没命中那发的 input`
- 按账单差值：`1 - 命中那发的花费 / 没命中那发的花费`

两个差得离谱（我们取 ≥15%）的时候**以 token 为准，并且把两个数都显示出来**。
原因是账单是**账号级**计数器：你体检的那两分钟里如果还在聊天、或者有后台推送，
那些钱会一起算进这一格。**别只报一个数然后假装它准。**

### 必须一起做的五条

1. **把发数和预估花费写在按钮上**，按下去之前就写（§7.1）。
   而且发数要**真计数**：强制被拒会多打一发，写死的数字会说谎（§7.2）。
2. **防重复的闸设在花钱那一端**，不是按钮上（§7.3～7.5）。
   最小可用的做法：同 `模型@地址` 有在途请求就等它、N 分钟内重复请求直接回上次结果。
   没有这道闸，连点五下就是扣五次钱。**复用的那次别记进历史**，
   否则历史里会出现两条一模一样的记录（§7.9）。
3. **每一条结论都带验证状态**：真打出来的 / 倒推的 / 没验的。
   一个不敢标"我没测到"的诊断工具，会把沉默变成好消息。
4. **测完把"这次拿什么测的"一起显示出来**，包括**体量**。
   14k 的玩具前缀命中，不代表 60k 的真实负载命中 ——
   前缀的**内容**像真的还不够，**大小也得同量级**，
   否则测出来的是"这个玩具能不能缓存"，不是"你的负载能不能缓存"。
   不写这一句，读者会拿它去改配置，然后配置越改越糟（§2、§6 都是这么来的）。
5. **建议和测量分开写**，而且**同一份证据在不同结论里要用同一个门槛**（§7.10），
   **只报事实和代价，不替人拍板**（§7.11）。

## 9. 我们没做 / 没验的

- ⚪️ 端点清单形式只跑通了**一次**真链路 + 3/3 的行为 A/B。**样本太小，不敢说稳。**
  已做成开关，默认关，出问题一秒切回。
- ⚪️ 端点清单形式下，写入类工具（`add_*` / `save_*`）拼错参数的实际概率未知。
  我们的判断是：**服务端 schema 校验 + 重拼循环**足以兜住，
  比「只搬只读工具」这种折中好 —— 因为写入类占工具块的 **58%**，
  只搬一半等于把大头留在原地，收益砍半而风险一点没减。
  **用范围换安全是最贵的那种保守。**
- ⚪️ 拆块（§1.3）改完之后还没在一条**真会缓存**的通道上验过收益。
- 🟡 「某些通道在做账号池负载均衡」是从 `8871 + 1517 = 10388` 这个算式倒推的，
  没有站方确认。
- 🟢 **四个显式缓存断点的槽位我们已经占满了**（人格 / 摘要 / 工具块末尾 / 倒数第二条历史），
  多轮工具调用时新追加的 `tool_result` 一个断点都排不上 —— 结构上跟
  [延伸阅读](#延伸阅读)里那篇 postmortem 的「修复前」一样。
  **量过之后是小钱**（近 14 天 1085 条回复只有 63 条走到第二轮，丢的只是断点之后那条尾巴），
  所以**没改**。写在这儿是因为结构风险真实存在，不是因为量出了损失。

## 延伸阅读

同一位作者的两篇东西，都推荐读，我们从中受益：

### 《tool-result cache postmortem》

CLWD FIELD NOTE 03（CODEX 5.6 SOL / CLWD/X PUBLICATION，2026-07-17）
<https://public.clwd.cc/tool-result-cache-postmortem/>

讲「写进去了，却永远命不中」：`tool_result` 明明有 `cache_creation_input_tokens`，
下一轮却读不回来。两层根因，我们读之前都不知道：

1. **Anthropic 最多只认四个显式缓存断点。** 四个槽位被人格 / 日记 / 摘要 / 滚动历史占满，
   `tool_result` 一个都排不上。
2. 给「只含工具结果」那条消息补断点时，实现里注入了一句说明文本，
   而那句话只存在于当次请求的副本里，下一轮重建时消失 → 前缀不匹配。

修法：把摘要那个断点让给 `tool_result`（5 分钟 TTL），
`cache_control` 直接挂在已有的 `tool_result` 块上、不新建文本块，
并确保协议转换层不吞掉元数据。最终布局按稳定性递减：
人格(1h) → 日记(1h) → 滚动历史(1h) → 工具结果(5min)。

**读完我们照着自查了一遍，两条结果记在这儿：**

- 我们的四个槽位同样是满的（人格 / 摘要 / 工具块末尾 / 倒数第二条历史），
  `tool_result` 同样排不上。不过我们的断点打在「倒数第二条历史」，
  多轮工具调用时新追加的块落在断点之后，丢的只是那条尾巴，
  近 14 天 1085 条回复里也只有 63 条走到第二轮 —— 对我们是小钱，所以没改。🟢
- 第二层那个坑我们恰好躲过了：每轮必变的实时状态早就挪进了最后一条用户消息，
  也就是断点之后（见 §1.3）。当时是为别的原因挪的，读完这篇才知道顺带避开了什么。🟢

这一节的思路来自这篇文章，我们只是拿它当清单自查了一遍。

### flagellum

Shitsuten，MIT · <https://github.com/Shitsuten/flagellum>

README 里有这么一句，讲的正是本文 §1.2 的同一条原理：

> 「工具定义排在 prompt 缓存前缀的最前面，内置工具的定义写死在代码里、顺序固定，
> 永远不会因为某个 MCP 服务抖动而打破整条缓存前缀。」

**这条原理他写在先。** 我们 §1.2 是 2026-08-14 自己量出来的（给工具块打 SHA，
发现长度一字不差而哈希每轮在变），读到这个仓库是第二天；
但先后不重要，写在先就该署，何况也不能排除中间有人跟我们提过。

**如果你也在用它**：它把内建工具的顺序钉死了，这一层是稳的；
外部 MCP 那部分（`getMcpTools()` 按遍历顺序累加，配一个 5 分钟缓存）
如果你接的 MCP 服务返回顺序不稳，§1.2 的修法可以直接接上去。
