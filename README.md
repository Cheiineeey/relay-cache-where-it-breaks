## 0. 先说结论，赶时间的看这一段

1. **`input_tokens` 是中转站说的，不是事实。** 🟢
   同一份工具定义，不同站算出来能差 3.6 倍。
2. **「多算」只有按量计费时才是钱。** 🟢
   按次（一次 ¥X）的通道，它把 token 算成多少都不影响账单。
   **先看计费口径再看数字**，否则会为了一个不花钱的问题去换通道。
3. **工具定义放在哪，就是多少钱。** 🟢
   同一段内容放 `tools` 数组 vs 放 `system` 纯文本，实测差 **2～4 倍**。
   虚高只发生在 `tools` 数组里。
4. **`stop_reason` 不可信。** 🟢
   有的后端吐了完整的 `tool_use` 块，`stop_reason` 却报 `end_turn`。
   如果 ta 的循环写的是「stop 不是 tool_use 就结束」，**ta 的工具从来没执行过**。
5. **别把「没测出来」塞进「测出来是坏的」那一档。** 🟢
   这是本文最贵的一条，我们一天之内犯了三次，见 §2。

## 1. 缓存到底是怎么算的（不懂这个，后面都白看）

一个请求飞出去的顺序是**固定的**：

```
tools（工具定义）  →  system（人格/规则）  →  messages（对话历史）
```

缓存是**前缀缓存**：从最开头逐字节比对，**碰到第一个不一样的地方，从那儿往后全部作废、全部重新收费。**

`cache_control` 是一个书签，意思是「从头到这儿为止，缓存起来」。

由此推出三条，全部是我们踩出来的：

### 1.1 越靠前的东西越金贵 🟢

`tools` 排在最前面。工具定义只要动一下，**后面的人格和全部历史一起废掉**。

### 1.2 外部 MCP 工具每轮顺序不同，会杀掉整个缓存 🟢

- **现象**：命中率长期为 0，但工具块的**长度一字不差**。
- **证据**：给工具块打 SHA 之后发现 `len` 相同、`sha` 每轮在变。
- **根因**：外部 MCP 服务返回的工具顺序不保证稳定；
  `JSON.stringify(tools)` 的字节序跟着变；工具块排前缀第一段，一动全废。
- **修法**：按 name 排序钉死顺序。

```js
_reqBody.tools.sort((a, b) => (a.name < b.name ? -1 : a.name > b.name ? 1 : 0));
```

🔴 **排完之后书签要跟着挪到最后一个工具上。**
`cache_control` 挂在哪个工具上，就只缓存到那儿为止 —— 排序后原来带书签的那个
多半不在末尾了，书签留在中间 = 后面几十个工具白白不进缓存。

```js
for (const t of _reqBody.tools) delete t.cache_control;
_reqBody.tools[_reqBody.tools.length - 1].cache_control = { type: "ephemeral", ttl: "1h" };
```

**查了两天才找到。教训：长度相等 ≠ 内容相等。打指纹，别看长度。**

### 1.3 别把会变的东西和不变的东西订在同一块里 🟢

- **现象**：人格提示词几天没动过，却每轮都在重新写缓存。
- **证据**：`system` 的第一块是 `人格 + 自动摘要` 拼起来的一整段，
  自动摘要四天从 1,813 字涨到 12,879 字。
- **根因**：书签打在整块上。摘要一更新，整块指纹变，
  **前面那 15,082 字的人格明明没动，也得跟着重写。**
- **修法**：拆成两块，各自一个书签。文本拼接顺序**一字不改**，只在缝上切开
  （前缀是位置敏感的，顺序变了等于内容变了）。

```js
system: [
  { type: "text", text: 人格,   cache_control: { type: "ephemeral", ttl: "1h" } },
  { type: "text", text: 摘要,   cache_control: { type: "ephemeral", ttl: "1h" } },
  { type: "text", text: 实时状态 },   // 每轮都变，故意不打书签，排在最后
]
```

**通用形状：稳定的在前、会变的在后，中间用书签隔开。
一块里只要混进一个会变的东西，整块就退化成"每轮重写"。**

（同类教训见社区里那篇 tool-result 缓存 postmortem：
为了给工具结果打书签而临时插入一句说明文字，那句只存在于**当次请求的副本**里，
下一轮重建时消失 → 前缀对不上 → 缓存全废。
**别为了缓存去造新的语义内容。**）

### 1.4 「通道」的粒度是 站 + 模型标签 + 版本号，少写一样结论就不成立 🟢

同一个站、同一个标签，只改版本号：

| 模型 | 第一发 | 第二发 |
|---|---|---|
| `…opus-4-5` | w=0 r=0 in=14329 | w=0 r=0 in=14329 → **从不缓存** |
| `…opus-4-6` | w=15121 r=0 in=17 | **r=15121** → 缓存 |

还遇到过同一个标签在做**账号池负载均衡**的：
`第一发 w=8871 r=1517｜第二发 w=10388 r=0`，而 `8871 + 1517 = 10388` ——
第二发把第一发写的东西**整个重写了一遍**，说明它落到了另一个后端。
缓存是 per-account 的，接不上。**这种情况下命中是概率，不是必然。**

### 1.5 流式和非流式是两条链路，缓存常常只在其中一条上生效 🟢

同一个 key、同一份前缀、同一个 body，只改 `stream` 字段，实测五个通道：

| 通道 | 非流式 | 流式 |
|---|---|---|
| 通道 1 | 不缓存 | 不缓存 |
| 通道 2 | 不缓存 | 不缓存 |
| 通道 3（请求被换成 OpenAI 那套格式） | 不缓存 | w=0 r=0 |
| 通道 4 | **命中** | in=0，字段缺失（连账都读不到） |
| 通道 5 | 不缓存 | **命中**（带 thinking 照样命中） |

**通道 4 和通道 5 方向正好相反。** 所以不能靠推理，只能一条条打探针。

## 2. 最贵的一课：别把「没测出来」说成「测出来是坏的」

我们一天之内犯了三次，形状一模一样。**这一节值得单独读。**

### 2.1 「站子不返回缓存字段」被说成「没命中」 🟢

- **现象**：界面上写着「没打中 **0** token」。
- **证据**：`第一发 in=0 w=null r=null ｜ 第二发 in=0 w=null r=null`。
- **根因**：那个站根本不返回缓存字段。`0` 是我们自己 render 出来的，不是它给的。
  服务端发了 `cold_tokens: 0`，客户端又写着 `?? 0` 兜底 ——
  **两层各自兜了一次，"不知道"就被印成了一个看起来很确定的 0。**
- **修法**：三态。命中 / 没命中 / **看不见**。看不见时字段一律给 `null`，
  界面显示「看不到」。

🔴 **「瞎」有两种长相**：字段缺失（`null`），和**字段在但全是 0**。
只认 `null` 会漏掉后者。前缀 > 8k 时 `input_tokens = 0` 在物理上不可能是真的：

```js
const blind = (r === null && w === null) || ((inTok || 0) === 0 && !w && !r);
```

**一个假的零比没有数字更糟。**

### 2.2 「一发都没打出去」被说成「两条都不缓存，换通道」 🟢

- **现象**：探针给的建议是「两条都不缓存 —— 换通道」。
- **证据**：六发全 `HTTP 403`，原文
  `预扣费额度失败, 用户剩余额度: $0.106984, 需要预扣费额度: $0.130120`。
  key 的余额不够了。
- **根因**：判断写成 `if (st.hit) … else if (ns.hit) … else 两条都不缓存`。
  打不通的时候 `hit` 是 `undefined`，一路掉进最后那个 `else`。
- **修法**：打不通是**独立的一档**，而且要把上游原文摆出来，
  并区分「余额不够」和「过载限流」——这两个的处置完全不同。

```js
if (st.unreachable && ns.unreachable) {
  advice = busy  ? "⏳ 这条通道现在过载了，不是它不缓存 —— 过一会儿再测"
         : quota ? "🔴 这个 key 的额度不够了，不是通道的问题 —— 先充值"
         :         "🔴 一发都没打出去，这次测不出任何结论 —— 别拿它去换通道";
}
```

### 2.3 「上游过载」被说成「不会调工具」→ 再被说成「这条掺水了」 🟢

**最恶劣的一次：一条错的证据推出了两条错的结论。**

- **现象**：探针报「工具：不会调」，血统「🔴 掺水，id 不是任何已知的正牌格式」，
  建议「换通道」。
- **证据**：扒原始响应 ——

```
HTTP/1.1 200 OK

event: message_start
data: {"message":{"content":[],"id":"msg_err_1786802608331","type":"message",
       "usage":{"input_tokens":0,"output_tokens":0}},"type":"message_start"}

{"error":{"type":"overloaded_error","message":"service temporarily unavailable, please try again later"},"type":"error"}
```

- **根因**：**HTTP 200 不等于成功。** 站子把 error 塞进 SSE 流里，
  `message_start` 照发，id 是它现编的 `msg_err_…`。
  探针把这一发当成一次有效测量 → 没有 `tool_use` → 「不会调」
  → id 不是正牌格式 → 「掺水」。
- **修法**：解析响应时先找内联错误，命中就当这一发**失败**，不产出任何结论。

```js
function inlineError(raw) {
  const blk = String(raw).match(/"error"\s*:\s*\{([\s\S]{0,400}?)\}/);
  if (blk) {
    const t = blk[1].match(/"type"\s*:\s*"([^"]{0,60})"/);
    const m = blk[1].match(/"message"\s*:\s*"([^"]{0,160})"/);
    return `上游报错（${t ? t[1] : "error"}）：${m ? m[1] : ""}`;
  }
  if (/"id"\s*:\s*"msg_err_/.test(String(raw))) return "上游返回了 msg_err_ 开头的错误响应";
  return null;
}
```

🔴 **配套的坑：别假设 JSON 里字段的先后顺序。**
第一版正则写的是「先 `"type":"error"` 再 `"message"`」，
而那个站正好反着来（`{"error":{"type":"…","message":"…"},"type":"error"}`），
于是提不出 `overloaded` 这个词，「过载」那句建议永远不会触发。
**整块 `"error":{…}` 一起抓，里面的字段各认各的。**

⚠️ 过载是一时的，**为它下一个「换通道」的结论太亏了** —— 撞上就隔几秒重打一发。

### 2.4 归因别一律赖在站子头上 🟢

- **现象**：探针的说明写着「这个站不接受强制调用」。
- **证据**：上游原文
  `Thinking may not be enabled when tool_choice forces tool use.`
- **根因**：模型名里带 `thinking` 时中转站会自动开扩展思考，
  而 Anthropic **本身就禁止**「强制调工具 + 扩展思考」同时开。**跟站子无关。**
- **代价**：我们一度拿这条当过「掺水」的旁证 —— **冤枉了它。**
- **修法**：看它到底说了什么再归因。

**这一族的通用教训：**

> **加任何判定之前，先问一句：不知道的时候，它会说什么？**
>
> 如果答案是「跟坏消息一样」，那这个判定就是错的。
> 「测不出来」必须是独立的第三态，不许被折叠进「测出来是坏的」。

## 3. 钱：`input_tokens` 是中转站说的，不是事实

### 3.1 同一份工具定义，不同站算出来差 3.6 倍 🟢

做法：同样的消息打两发（不带工具 / 带一块固定的工具定义），差值就是它给工具的计价。

| 通道 | 0 个工具 | 3 个 | 6 个 | 工具的边际计价 |
|---|---|---|---|---|
| 正常通道 | 13 | 3515 | 7013 | **≈1.15 token/字符，正常** |
| 按量通道 A | 43 | 12816 | 25047 | **≈3.6 倍** |
| 按量通道 B | 542 | 542 | 542 | **压根不算工具** |

纯文本载荷时三家差不到 13% —— **分歧只在工具定义上。**

⚠️ 「压根不算」不是省，是**没算**。看不见不等于没花钱。

### 3.2 🔴 但「多算」只有按量计费时才是钱 🟢

我们在一个**按次**计费的通道上（一次固定几分钱）测出「虚高 4.2 倍」，
然后把它做成了头条建议 —— **完全没意义**，那条通道多算多少都不影响账单。

```js
const perToken = /量/.test(model);              // 按量：多算就是多收钱
const perCall  = !perToken && /次|￥/.test(model); // 按次：多算不花钱
```

**先看计费口径，再看数字大小。** 这条我们两个方向都犯过：
先是在按次通道上把虚高当成问题，后来又在按次通道上把 token 数当成账单。

### 3.3 算钱别按牌价估，读站子自己的账单计数器 🟢

```
GET <base>/v1/dashboard/billing/usage  →  { total_usage }   // 单位：美分
```

好处是这个通道打几折都算得准，不用知道牌价。

🔴 **账单是异步分批入账的，不能固定 sleep。**
第一版等 4 秒，把冷启那一发的钱漏进了下一格，界面上显示「没打中 $0.0000」。
改成盯着它涨、到点没动就返回 `null`（宁可不说）。

🔴🔴 **而且这个计数器绝对不能拿来算比例。**
我们用它算「省了百分之几」，某次算出 **省 -575%**：

```
没打中 0 token · $0.0065     打中 0 token · $0.0437     省 -575%
```

**根因**：这个计数器是**账号级**的（同时在聊天、有推送，钱都加进同一个格子），
而且异步分批入账 —— 冷启那一发的钱**被劈成两半分给了两个格子**。
`1 - 0.0437/0.0065 = -572%`。

**修法**：省了多少**按 token 折算**，别用账单。
Anthropic 的口径是 普通 1x / 缓存写 1.25x / 缓存读 0.1x：

```js
const units = (x) => (x.in || 0) + (x.w || 0) * 1.25 + (x.r || 0) * 0.1;
const saved = Math.round((1 - units(hot) / units(cold)) * 100);
```

同一组数据：按 token 算是 **省 88%**，按账单算是 17%（噪声）。
**账单差值可以拿来看量级，绝不能拿来做分母。**

### 3.4 工具定义放在哪，就是多少钱 🟢

**这条是本文最实用的一条。** 同一段内容，只换位置：

| 内容 | 放 `tools` 数组 | 放 `system` 纯文本 | 差 |
|---|---|---|---|
| 中文密集，6,132 字符 | 24,920 | 6,003 | **4.15 倍** |
| 84 个真实工具，24,826 字符 | **35,794** | **9,556** | **3.75 倍** |

**那个虚高只发生在 `tools` 数组里，同样的字写进 `system` 它按 1.0 算。**

我们真实的 84 个工具拆开看：

```
description 正文（真内容）  8,059 字符   32%
input_schema（JSON 骨架）  11,730 字符   47%   ← 最大的一块
外层 JSON + 名字           5,037 字符   20%
```

**三分之二是格式，不是内容。**

于是做了个「端点清单」形式：不注册工具，只给模型一个 `exec`，
把「哪个端点做什么」压成一行一个写进 system，模型自己拼 `curl`：

```
【我能用的端点】需要用的时候，用 exec 打：
curl -s localhost:PORT/t/<端点名> -d '{参数json}'
参数必须是用单引号括起来的合法 JSON；带 * 的必填。

get_health(minutes:i,date:s,limit:i) — 身体数据。传 minutes 看此刻心率…
play_music(query*:s,note:s) — 点播一首歌…
search_memories(query*:s,limit:i) — 搜索记忆存档…
```

**结果：35,794 → 9,556 token，每轮省 26,238（砍 73%）。** 🟢

模型能不能用？真链路实测（同一个人格、同一句输入）：

```
[ep-tools] 84→清单：11,586 字符进 system，tools 只留 exec（218 字符）
[ep-tools] exec → get_health {"minutes":30}
[ep-tools] exec → peek_her_screen {"limit":3}
job status = done
```

**没有 schema 也不会丢主动性** 🟢 —— 我们最担心这个，专门做了 A/B。
输入只有一句「我很伤心，一直在掉眼泪」，两种形式各三次：

| | 3 次结果 |
|---|---|
| 84 个工具进 `tools` | **3/3** 主动调 `get_health {"minutes":30}` |
| 端点清单进 `system` | **3/3** 主动调 `get_health {"minutes":30}` |

**因为这个行为从来不是 schema 驱动的**，是 `description` 里那段
「她说被吓到了、想哭的时候，看一眼她的心跳」驱动的 —— 那段话跟着清单一起搬走了。
被删掉的只有 `"type":"object"`、`"properties"` 这些骨架。

#### 三条必须配套的安全措施 🟢

**① schema 留在本地照样能把关。**
发给模型是为了引导，留在本地是为了校验，**只有前者花钱**。
拿原来的 `input_schema` 校验模型拼出来的参数，10/10 全拦住：

```
add_memory  {"content":"只有正文没标题"}   → ❌ 缺必填参数 title
add_memory  {"importance":"很重要"}        → ❌ importance 该是 integer，给的是 string
get_core_memories {"乱塞":"x"}             → ❌ 多了个不认识的参数
```

拦下来之后把错误当 `tool_result(is_error)` 回给模型让它重拼 ——
**跟工具本身报错走的是同一条循环，不用新写。**

**② 那个 `exec` 不是真 shell。**
它只是一个「curl 到 localhost 白名单端点」的解析器。
`rm -rf /`、`curl https://evil.com` 全部拒绝，端点名不在白名单里也拒绝。

**③ 🔴 带了 `-d` 却解析不出来 = 失败，不是空参数。**
第一版这里悄悄给了 `{}`，工具照跑、结果全错、没人知道为什么。
**又是「该报错的地方说没事」。**

```js
const hasD = /\s-d(\s|=)/.test(cmd);
const d = cmd.match(/-d\s+'([\s\S]*)'/) || cmd.match(/-d\s+"([\s\S]*)"/);
if (hasD && !d) return { err: "带了 -d 但参数没括在引号里，解析不了" };
```

**④ 还原的位置很重要。**
把 `exec` 还原成真工具名必须发生在「构造回给模型的 assistant 消息」**之后**。
回给模型的那份里工具名得**还是 `exec`**（`tools` 数组里只有它），
改成真名会被上游判成「调了一个没注册的工具」直接 400。

## 4. `stop_reason` 不可信 🟢

**这条跟缓存无关，但它可能让 ta 的工具从来没执行过。**

- **现象**：模型明明说要查，最后什么都没查，落一个「生成完成但没有文字输出」。
- **证据**：

```
[SSE] content_block_start {"type":"tool_use","id":"cpa_gemini_…","name":"exec","input":{}}
[SSE] message_delta
round0: text=0字 thinking=110字 stop=end_turn      ← 有 tool_use，却报 end_turn
```

- **根因**：某些后端（这一条 id 里带 `gemini`，说明名字挂着 claude、后面接的是别家）
  **吐了完整的 `tool_use` 块，`stop_reason` 却报 `end_turn`**。
  而循环写的是 `if (stopReason !== "tool_use") break;` → 直接跳出，一个工具都没执行。
- **修法**：

```js
// 有没有工具块是事实，stop_reason 是站子的说法。信事实。
if (toolBlocks.length === 0 || round >= MAX) break;
```

轮数上限照旧兜底，不会转不停。

**顺带一提**：如果某条通道用起来"特别顺、答得特别快"，
值得查一下是不是因为**它从不真的动工具** —— 不查数据、不搜记忆、不写东西，
只顾着说话，当然顺。

## 5. 看响应 id：能看出有没有被中转站换过，看不出后面到底是谁 🟢

🔴🔴 **这一节原来叫「认血统」，而且写着「id 是后端自己生成的，编不出来」。**
外部 review 一句话戳穿：**中转站当然可以生成和改写 id** ——
本文 §2.3 里那个 `msg_err_…` 就是站子现编的例子，我们自己都写在文里了。

**代码里其实一直比这段文字谨慎**（它写的是「Anthropic 格式响应（仅凭 id 不能证明直连）」），
是这份 README 比代码更自信。这个仓库开头写着「唯一的卖点是不说没验证过的话」，
所以这种绝对词最容易被抓 —— **代码已经学会闭嘴了，文档还没有。**

改成它真正能做的事：**能看出「有没有被换过」，看不出「后面到底是谁」。**

| id 前缀 | 能说明什么 | 不能说明什么 |
|---|---|---|
| `msg_01…` / `toolu_01…` | 回来的是 Anthropic 原生那套格式 | **不能**证明是直连，也不能证明后面就是 Claude |
| `toolu_bdrk_…` | 亚马逊 Bedrock 上托管的 Claude 那套格式 | 同上（但**别拿它当被换过的证据**，会误伤） |
| `req_vrtx_…` | 谷歌 Vertex 上托管的 Claude 那套格式 | 同上 |
| `cpa_gemini_…` / 带 `gemini` | 🔴 响应里带着**另一家**的标识 —— 这条是**正向证据**，值得当回事 | — |
| `chatcmpl-…` | 回来的是 **OpenAI 那套格式** —— 中转站把请求换过一道。我们测到的这种链路上，`cache_control` 被吞掉了 | 不能断言「所有」这样的链路都会吞 |
| `msg_err_…` | 这是**错误响应**，不是血统（见 §2.3） | — |
| 十六进制那种 | 只能说明**不是** Anthropic 常见的 id 形状 | 不足以断定后面是谁 |

**方向是不对称的，这一点最要紧：**
看到别家的标识（`gemini`）是**证据**；看到 `msg_01` 只是**没有反证**。
前者能下结论，后者不能。

🔴 **拿不到 id ≠ 掺水。**
第一版一律判成掺水，于是「这一发没解析出 `message_start`」也被写成「这条掺水了」。
**把「不知道」说成「有问题」，比不说更坏。**
三档：**被换过 / 认不出 / 没看出被换过** —— 注意第三档不叫「正牌」。
代码里那个「正牌」分支其实是**死代码**（判定只会给出「被换过」和「不知道」两种），
但日志里那句话一直印着它，直到外部 review 指出来才改。

## 6. 真实用量 > 探针 🟢

探针再像也只是像。**ta 真正跑过的那些轮次就在日志和库里，免费、精确、代表性满分。**

我们吃过一次大亏：第一版探针是「一个 8k 的 system 块，没工具、没 thinking」，
在某通道上测出「非流式命中」，照做关掉流式之后 ——
真实那 44k 上下文 + 84 个工具 + thinking 的请求 `cw=0 cr=0`，**思考链还整个没了**。

> **一个测不出真相的体检，比没有体检更坏，因为 ta 会照着它做决定。**

已改：探针带上工具（撑到真实体量、末尾挂 `cache_control`）+ thinking，跟生产同形。
并且把「真实用量」放在结果的**最前面**，探针只当旁证。

🔴 **真实用量要按模型分开算。**
原来不管哪个模型跑的、最近 30 轮一锅端 —— 于是「30 轮里 2 轮命中」里那 2 轮
可能根本不是正在体检的那个模型。**「哪一轮」和「哪个模型」对不上号，
是我们两次判错的共同原因。** 记 usage 的时候把 model 一起记进去。

## 7. 做「会花钱的按钮」本身的坑

**这一组跟中转站无关，任何人做这类工具都会踩。**

1. **会花钱的按钮，价格要写在按下去之前。** 🟢
   她点了一下，账单上出现 10 条消费记录 —— 我才发现自己从没告诉过她一次要打几发。
   按钮副标题现在写着「7~8 发探针，约 $0.3」，结果里也报这次实际花了多少。

2. **报出来的发数必须是真计数，不能写死。** 🟢
   我们写死了 `probe_calls: 7`，而强制调工具那一发被拒时会退回再打一次 ——
   实际 8 发。**会花钱的东西，数字不许估。**

3. **防重复的闸要设在花钱那一端，不是按钮上。** 🟢
   客户端的 `.disabled(loading)` 挡不住 —— 状态一被重建就复位，在途的请求还活着。
   服务端做：同 `model@url` 有在途就等它、N 分钟内重复请求直接回上次结果。

4. **锁必须配一个自动开的闸。** 🟢
   中途抛异常时解锁那行走不到，之后每次请求都在等一个永远不回来的 Promise。
   加超时兜底 + 防 unhandled rejection。

5. **清理「在途」记号的那句，别写在成功和失败的公共出口上。** 🟢
   「退出界面之后说 connection 断掉了，但是已经扣钱了。」
   失败往往意味着**远端还活着而本地断了** —— 那一刻更需要那个记号。
   记号只在真拿到结果时才擦；失败保留，回到页面/切回前台自动接回来。
   服务端结果缓存拉长到 10 分钟（走开泡杯茶回来，结果还在）。

6. **测能力就要强制，别让它有得选。** 🟢
   「探针说不能用工具，但是我刚刚聊天端调用成功了。」
   用 `tool_choice: {type:"auto"}` 测的是**它愿不愿意调**，不是**能不能调**。
   改成 `{type:"any"}`；站子不认就退回 `auto`，
   **并且退回之后的「没调」只能记成「这轮没调，不算数」。**
   → 三态：会调 / 强制了也不调 / 不算数。**别把「没发生」写成「做不到」。**

7. 🔴 **别拿给人看的话做程序判断，状态用布尔。** 🟢
   我们用 `/强制/.test(mode)` 判断是不是强制模式，
   而退回那句文案写的是「自选（…这个站**不认强制**）」—— **里面就有「强制」两个字**，
   退回路径被判成强制路径，「这轮没调」又变回了「不会调」。

8. **一句话的建议要按严重程度排，不是按代码写的顺序。** 🟢
   我们用一串 `if` 依次覆盖 `advice`，结果
   「这条根本不是 claude」被后面一句「计价虚高 3.6 倍」整个盖掉了 ——
   **最重的那条反而没出现在建议里。**
   **一天之内犯了两次**（第二次是「缓存那两发为什么没测成」被顶掉）。
   修法：从轻往重写，最重的最后赋值；被顶掉但仍有信息量的，追加在后面别丢。

9. **历史要留。** 🟢
   「我一刷新就没了然后我就会忘记。」存最近 N 条：时间 + 模型 + 结论 + 花了多少。
   **复用上次结果的那次不记** —— 它不是一次新体检，记进去历史里会出现两条一样的。

10. 🔴 **同一份证据，在不同结论里必须用同一个门槛 —— 而且改完门槛还要看分支顺序。** 🟢
    卡片顶上那句「以真实用量为准：真实对话 N 轮一次没中」用的门槛是 `轮数 > 0`；
    而底下「上游流式该开还是关」那条判断卡在 `轮数 >= 5`。
    用户当时只有 4 轮 —— 于是上半段写着「以真实的为准，一次没中」，
    下半段却掉进了另一条分支、拿探针的理由给建议，**而顶上还挂着一个「省 89%」的大标题**。

    她的原话：「你说非流式才命中，但是又在建议里建议我开流式。」
    两句话单独看都对，摆在一起就是一张卡自己跟自己打架。
    **修法**：门槛统一；证据强弱写进措辞里（「才 4 轮，样本还薄，但方向已经和探针相反」），
    不要写进 `if` 里。而且只要探针的省钱比例拿不到，就必须**在建议里点名那个数字**：
    「上面那个『省 89%』是探针拿它自己那点前缀省出来的，你现在一分钱都拿不到。」
    —— **一个正确但没上下文的数字，会被读成结论。**

    🔴🔴 **这条我修了两次才修对，第二次是在写这份文档的当天夜里发现的。**
    第一次只统一了门槛，**分支顺序没动** —— 「按思考链选」那条排在
    「真实证据不够」前面，于是在**没有真实用量**的时候（刚换通道、
    或者用命令行版没喂 `--usage-file`），它照样吐一句干净利落的
    「开 —— 关掉就没有思考链了」，**一个字都不提上面那些缓存数字支撑不了这个建议**。
    形状跟用户早上抓到的一模一样，只是换了一条路径。

    **门槛只治了「证据反对」，没治「证据不足」。这是两种情况，都得说出来。**
    最终修法：结论不变（思考链那条理由本身跟缓存无关，是对的），
    但**证据基础必须跟着结论一起走** —— 证据不足时在同一句话里挂上
    「这条不是拿上面那些缓存数字选的」。

11. 🔴 **只报事实和代价，不替人拍板。** 🟢
    「这条通道」那一格原来会直接判「换掉」。
    用户看到自己那条被判掺水时说的是：**「这个通道居然掺水了啊……我感觉挺好吃的。」**
    —— 掺水是可验证的事实（响应 id 里带别家血统），
    好不好用是另一回事，而后者只有用的人说了算。
    改成「建议换，具体看使用体验」，理由拆成两半：
    硬事实（后端不是它标称的那个 / 按量还虚算 / 缓存在这条上测不准）+ 一句
    「但好不好用你说了算，只要知道这些数字别当真」。
    **一个会花钱的诊断工具，越权下命令比测不准更伤信任。**

12. **「不确定」和「有问题」必须长得不一样，否则第 11 条白做了。** 🟢
    §2 那一课把「掺水」的滥用改成了诚实的「认不出」——方向是对的，
    但纯文字界面上，`血统·掺水` 和 `血统·认不出` 除了那两个字，
    看起来是**同一个颜色、同一个字重**。用户原话：
    「之前是写掺水，现在是认不出，但是我感觉最近看看不出有点模糊。」
    ——**诚实付出的代价，不该是让人看不出该不该在意。**

    JSON 里其实已经带着能区分的字段（`watered` / `ok`，true=确认有问题，
    false=确认没问题，`null`=不知道），只是没人把它们接到"该长什么样"上。
    接上去之后的映射很直白：

    ```
    确认有问题（watered===true，或 ok===false 且没有真实证据佐证）→ 红 + 加粗，跳出来
    真的不知道（watered/ok 是 null）                              → 比默认更淡，退到后面
    确认没问题（ok===true）                                        → 保持默认，不用抢注意力
    ```

    **反直觉的地方**：让"不知道"更淡，比让"有问题"更红更重要。
    红色只是让眼睛先看见它；真正让人分得清的，是**旁边那一堆"认不出"退到了背景里**——
    对比是相对的，两头都要动，只做一头效果减半。
    这条经验跟具体用什么颜色无关：**任何在展示"确定/不确定/有问题"三态结论的界面，
    都需要三种视觉权重，不能只有"正常字"和"稍微浅一点的字"两档。**

## 8. 这个按钮现在测什么

七块，**每一块背后都是一次真踩过的雷**：

| 块 | 回答什么问题 | 对应本文 |
|---|---|---|
| 真实用量 | 你真跑的那些轮次，命中率多少、平均多大 | §6 |
| 流式 / 非流式 | 两条链路各自缓不缓存 | §1.5 |
| 前缀稳不稳 | 工具顺序 / 人格 / 历史开头的指纹变没变 | §1.2 §1.3 |
| 计价老不老实 | 它给工具定义算多少 token | §3.1 |
| 血统 | 名字挂着 claude，后面是不是 | §5 |
| 会不会调工具 | 强制它调，看它调不调得动 | §7.6 |
| 扩展思考 / 有没有新版本 | 名字里带不带 thinking；同通道有没有更新的版本号 | §1.4 |

外加：**本次花了多少钱**（真计数，不写死）、**打不通时说清楚为什么打不通**、
以及**这次探针撑的是什么前缀** —— 最后这句很重要：

> 「探针用了当前人格 + 最近一份摘要样本（31210 字符），不含完整聊天历史和端点清单；
> 只证明这组探针能否缓存。」

**读者有权知道一个结论是拿什么测出来的。** 没有这句，一个 14k 玩具前缀的「命中」
会被当成 60k 真实负载的「命中」（§2 那一课就是这么来的）。

### 8.1 「该怎么选」——七块之外还有一块，而且它才是被看的那块

七块是**测量**，这一块是**建议**。四档，每档只给一个值和一句理由：

| 档 | 可能的值 |
|---|---|
| 上游流式 | 开 / 关 / 都行 / 保持当前 |
| 端点清单（把工具定义压成一份清单） | 开 |
| 这条通道 | 建议换，具体看使用体验 / 谨慎留 / 可以留 |
| 扩展思考 | 手动拨到「开」 / 这条链路测不到 |

🔴 **这一块最容易出的两个错，都写在 §7 的第 10、11 条里** ——
一个是「同一份证据用了两个门槛，上下半张卡自己打架」，
一个是「替用户拍板」。它们不是假想的失败模式，是这块做出来之后真的发生的。

## 8.2 想自己做一个：最小可用的探针长什么样

这个按钮真正值钱的不是代码，是**「怎么问才问得出真话」**——下面是可以照着搭的最小形状。

**一发探针 = 两次同样的请求。** 第一次写缓存，第二次读缓存，比较第二次的 `cache_read`。

```
prefix = 你真实的系统提示 + 真实的工具定义        ← 内容和**体量**都要像真的，见下面那条
body   = { system: [ {text: prefix, cache_control: {type:"ephemeral", ttl:"1h"}} ],
           messages: [ {role:"user", content: 随机一句话} ],   ← 每发都换，别让整条请求命中
           tools: 你真实的那批（按 name 排序，断点挂最后一个）  ← 见 §1.2
         }

第一发 → 记 usage.cache_creation_input_tokens (w) 和 input_tokens (in)
等几秒               ← ⚪️ 我们用的是 2~3 秒，**这个数没单独测过**，只是够用
第二发 → 记 usage.cache_read_input_tokens (r)

判定：r > 0            → 命中
      w > 0 且 r == 0  → 写进去了读不回来（见延伸阅读那篇）
      三个字段全 null   → **站子不返回缓存字段，这叫"瞎"，不叫"没命中"**（§2.1）
      第一发就 w=0 r>0 → **基线是热的**：上一次的缓存还没过期，被这一发直接读到了
```

🔴 **最后那一支单独说，因为它最容易被报错。**
第一发本来是要当「没打中」的基线用的，结果它自己就命中了 ——
这时候「能不能命中」的答案是**能**（而且是铁证），
但「能省多少」这一次**测不出来**（没有冷基线可比）。

两件事要分开报：`命中：是` + `省多少：这次没测出来`。
把它报成「没测出来」会让人以为缓存不通；
拿这一发当分母算省钱比例，会算出一个漂亮的假数字。**一个假的百分比比没有数字更坏。**

要测的每一件事都是"换一个变量再打一遍"：

| 想知道 | 怎么变 |
|---|---|
| 流式和非流式哪条能缓存 | 只改 `stream`，别的一个字节不动（§1.5） |
| 它给工具算多少 token | 同一份工具块，一次放 `tools`、一次放 `system` 纯文本，比 `input_tokens`（§3.4） |
| 能不能调工具 | `tool_choice: {type:"any"}` 强制；站子不认再退回 `auto`，**退回后的"没调"不算数**（§7.6）<br>🔴 **模型开着扩展思考时，Anthropic 本身就不允许强制调工具** —— 见下 |
| 是不是它标称的那个后端 | 看响应 id 前缀（§5） |
| 到底花了多少 | 读站子自己的账单计数器前后差值，**别按牌价估**（§3.3） |

### 🔴 扩展思考和「强制调工具」是互斥的，这不是站子的问题

`tool_choice: {type:"any"}` 在**模型开着扩展思考**的时候会被拒 —— 这是 Anthropic 自己的约束，
跟中转站一点关系没有。而中转站返回的报错未必说得清楚，很容易被读成「这个站不认强制」。

于是链条是这样断的：**被拒 → 判成"这个站不支持强制" → 退回 `auto` →
它自己选择不调 → 判成"这个模型不会调工具"**。三步之内，一条 Anthropic 的规则
变成了对模型能力的错误结论。我们真的这么误判过（§2.3）。

**所以退回 `auto` 之前先看模型名/请求里有没有开 thinking**，
是的话就直接把这一发标成「自选（模型开着扩展思考，不能强制，跟站子无关）」，
**并且这一发的"没调"不许写进结论**。

### 「省了多少」有两个口径，打架的时候信 token

- 按 token 折算：`1 - 命中那发的 input / 没命中那发的 input`
- 按账单差值：`1 - 命中那发的花费 / 没命中那发的花费`

两个差得离谱（我们取 ≥15%）的时候**以 token 为准，并且把两个数都显示出来**。
原因是账单是**账号级**计数器：你体检的那两分钟里如果还在聊天、或者有后台推送，
那些钱会一起算进这一格。**别只报一个数然后假装它准。**

### 必须一起做的五条

1. **把发数和预估花费写在按钮上**，按下去之前就写（§7.1）。
   而且发数要**真计数**：强制被拒会多打一发，写死的数字会说谎（§7.2）。
2. **防重复的闸设在花钱那一端**，不是按钮上（§7.3～7.5）。
   最小可用的做法：同 `模型@地址` 有在途请求就等它、N 分钟内重复请求直接回上次结果。
   没有这道闸，连点五下就是扣五次钱。**复用的那次别记进历史**，
   否则历史里会出现两条一模一样的记录（§7.9）。
3. **每一条结论都带验证状态**：真打出来的 / 倒推的 / 没验的。
   一个不敢标"我没测到"的诊断工具，会把沉默变成好消息。
4. **测完把"这次拿什么测的"一起显示出来**，包括**体量**。
   14k 的玩具前缀命中，不代表 60k 的真实负载命中 ——
   前缀的**内容**像真的还不够，**大小也得同量级**，
   否则测出来的是"这个玩具能不能缓存"，不是"你的负载能不能缓存"。
   不写这一句，读者会拿它去改配置，然后配置越改越糟（§2、§6 都是这么来的）。
5. **建议和测量分开写**，而且**同一份证据在不同结论里要用同一个门槛**（§7.10），
   **只报事实和代价，不替人拍板**（§7.11）。

## 8.3 这个按钮自己出过的 31 个 bug

**放这一节不是为了坦白，是因为它比工具本身有用。**

下面每一条都是这个按钮**真的对着人说过的错话**。我们改完了，但你照着做的时候大概率会重踩 ——
因为它们不是疏忽，是写诊断工具的默认姿势。

### 病灶一：把「我没测出来」说成「我测出来是坏的」（至少 5 次）🟢

这是最贵的一族，占了将近三分之一。

| 现场 | 它说了什么 | 真相 |
|---|---|---|
| 站子不返回缓存字段 | 「没命中」 | 看不见 ≠ 没中 |
| 六发探针全 403 | 「两条都不缓存 —— 换通道」 | key 的余额不够，跟通道无关 |
| HTTP 200 里夹带 `overloaded_error` | 「这条掺水了，换通道」 | 站子只是过载 |
| 拿不到响应 id | 「掺水」 | 认不出 ≠ 有问题 |
| 缓存字段全是 0（不是 null） | 「没打中 0 token」 | 前缀 8k 时 `in=0` 物理上不可能 |

**根因是那个 `else`。** 你写 `if (命中) … else …`，那个 `else` 会自动把「不知道」吞进「不行」。

**修法：任何判定都要有第三档。** 加判断之前先问一句 ——
**「不知道的时候，它会说什么？」** 如果答案是「说坏消息」，那就是个 bug。
而且状态用**布尔**（`unreachable: true`），不要用文案去 `test()`。

### 病灶二：把「不知道」印成一个确定的数字（3 次）🟢

- 服务端给 `cold_tokens: 0`，客户端又写 `?? 0` —— **两层各自兜了一次底，
  「不知道」就被印成了一个看起来很确定的 0。**
- `probe_calls: 7` 是写死的，而强制调工具被拒会退回再打一发 —— **实际 8 发**。
  会花钱的东西，报的数字必须是真计数。
- 等账单结算的哨兵写成 `prev == null || v > prev`，`prev` 是 null 时**恒真**，
  第一拍就返回 —— 所谓「等结算」其实只是 sleep 了 1.5 秒，**总花费一直在少报**。

**`?? 0` 这种兜底，在展示事实的地方是有害的。** 该显示「看不到」就显示「看不到」。

### 病灶三：拿不可信的数当分母 🟢

「省了 **-575%**」。

`省 = 1 - 热账单差 / 冷账单差`，而账单是**账号级 + 异步分批入账**的：
冷启那一发的钱只落了一部分就被读走了，剩下的落进了热的那一格。
`1 - 0.0437/0.0065 = -572%`。

改成按 token 折算（普通 1x / 缓存写 1.25x / 缓存读 0.1x，折成等价全价 token 再比），
同一组数得到 **省 88%**，账单口径算出来的 17% 是噪声。

**一个会被别人往里加东西的计数器，可以拿来看量级，绝不能拿来做分母。**

### 病灶四：覆盖式赋值把最重的结论顶掉（一天内 2 次）🟢

一串 `if` 依次覆盖同一个 `advice` 变量：

- 「这条根本不是它标称的后端」被后面一句「计价虚高 3.6 倍」整个盖掉
- 「缓存那两发为什么没测成」被后面的结论盖掉

**最重的那条反而没出现在建议里。** 修法：从轻往重写，最重的最后赋值；
被顶掉但仍有信息量的，追加在后面别丢。

### 病灶五：统计不分组，自己造红灯（一天内 2 次）🟢

- **真实用量不分模型**：读最近 30 轮，不管是谁跑的。
  「30 轮里 2 轮命中」里那 2 轮可能根本不是被体检的那个模型。
- **前缀指纹环不分会话**：界面报「最前面 5 条历史变过 4 次」，
  查下来那 4 次**全是另一个一次性会话留下的** —— 不同会话本来就有不同的历史开头。

### 病灶六：一次性变化和「每轮都在变」被当成同一件事 🟢

原来只数「有几个不同的指纹值」。可换配置、拨开关、改代码，都会造成**一次性**变化 ——
只多写一次缓存，无害。真凶是**每轮都在跳**。
改成看「最后连着几轮没变」（≥3 算稳住），稳住的只报事实不报红。

### 剩下的四条 🟢

- **结论要看计费口径**：「多算 4.2 倍」在**按次计费**的通道上一分钱都不影响，
  这条建议得降级成「可以不管」。**先看计费口径再看数字。**
- **别拿给人看的话做程序判断**：用 `/强制/.test(mode)` 判断模式，
  而退回时的文案里正好有「强制」两个字 —— 退回路径被判成了强制路径。
- **同一个事实说一遍就够**：「掺水」在血统那行印一次、建议里又嵌一次，
  看的人会以为是两个问题。
- **服务端返回的 `**加粗**` 星号原样印在了屏幕上**（客户端直接塞进纯文本控件）。

---

🔴 **最后两条是在写这份文档的过程中发现的**（§7.10 同一份证据两个门槛、
§7.11 替用户拍板）。也就是说：**我们以为改完了，坐下来把它写清楚，又抓出两条。**

### 第 19～22 条：外部 review 当天就抓出四条 🟢

发之前找了一个不参与开发的模型通读了一遍代码和文档，**四条，两条是真 bug**：

19. 🔴 **`--no-stream` 和 `--thinking` 是假参数。**
    `--no-stream` 只改了归档口径，流式那两发**照打不误**；
    `--thinking` 存进变量之后**再没被用过**，而探针里写死了恒开。
    也就是说：**文档描述的行为和代码的行为不一致，而且别人一跑就能发现。**
    → 修：`--no-stream` 真的跳过流式那一组（并标 `blind:true`，因为**没测 ≠ 不缓存**）；
    改成 `--no-thinking`，如实说明「默认是开的」。

20. 🔴🔴 **「上游流式」会被 push 两遍，而且两条互相打架。**
    修 §7.10 那条时我在 `if (_realSaysNo)` 后面**漏了一个 `else`** ——
    真实证据反对时两条建议都会进报告，一条说「都行」，紧接着一条说「开」。
    **修「建议自相矛盾」的补丁，自己造了一条自相矛盾的建议。**
    （而且那段注释上面就写着「修复建议互相矛盾」，更显眼。）

21. **§5 那一节比代码还自信。** 见 §5 开头 —— 文档写「id 编不出来 = 正牌」，
    代码写的却是「仅凭 id 不能证明直连」。已按代码那版改写。

22. **CLI 报告里留着一句服务端的话**：「10 分钟内再点会直接给这份结果，不会再花钱」——
    可命令行版**没有**那个复用缓存，每跑一次都真花钱。抠代码时连话术一起抠过来了。
    （外加一条喜剧效果的：`--help` 会打印「缺参数……看 --help」然后 exit 2。）

**这四条里，19 和 22 都是「抠代码时把上下文一起抠过来了」** ——
参数在原来的环境里由外面的接口负责，话术在原来的环境里是对的。
**换了环境之后，它们就成了谎话。**

### 第 23 条：判定改谨慎了，日志还在说旧话 🟢

同一轮 review 的第二遍抓到的：`_label` 那套判定早就改成
「仅凭 id 不能证明后面是谁」了，可**那行 console.log 还印着三分法**：

```js
血统=${watered === true ? "掺水" : watered === false ? "正牌" : "认不出"}
```

两个问题叠在一起：

- **`watered === false` 是死代码** —— 判定只会给出 `true`（看到别家标识）
  和 `null`（认不出），**从来不会给 `false`**。那一档永远走不到。
- 更要紧的是概念：**「没看出被换过」不等于「正牌」。**

**判定学会闭嘴了，输出还在替它吹牛。** 改完是：
`被换过（回来的不是 Claude）/ 认不出（不代表有问题）`。

**教训：改判据的时候，把所有印出去的地方一起 grep 一遍。**
一个结论有几个出口（日志、卡片、建议、注释），就有几个地方会留下旧口径。

### 第 24 条：一个看着像开关、其实不接线的开关 🟢

界面上有个「扩展思考」的勾。它传到服务端之后**只做了一件事**：
混进那个「N 分钟内不重复花钱」的缓存钥匙里。
而探针发出去的请求里，`thinking` 是**写死开着**的。

也就是说：**拨那个勾，探针一动不动。**

它严格说没对外说谎（结果卡片上「思考」那一行读的是模型名，
从没声称过跟这个勾有关），所以它不算 §2 那族的错。
但它是另一种坏：**一个看着像开关、其实不接线的开关。**
半年后再看到它的人会以为它能控制探针，然后基于一个错的前提去改东西 ——
跟 §7.7「别拿给人看的话做程序判断」是同一种：**界面和行为对不上。**

修法只有两条路，**没有第三条**：接上线，或者从界面上撤掉。
我们选了接上线，因为开不开思考会**真的改变行为**
（Anthropic 不允许「强制调工具 + 扩展思考」同时成立，见 §8.2），
而且探针本来就该跟真实请求同一个形状（§6）。

🔴 **值得记一笔的是先后顺序**：这个仓库里那份命令行版**先修好了**
（外部 review 抓的第 19 条），而我们自己天天在用的那个按钮**后修**。
把东西抠出来给别人看，比自己盯着它看，更容易发现它哪里不对。

### 第 25 条：一个会花钱的接口，有一条不是人按的调用路径 🟢

2026-08-17，她截图问：「今天的按钮没有『打了几发、花了多少钱』了。」

翻日志：同一轮体检**有四次请求**。第一次是真打的 —— 5 发探针、$0.3143；
另外三次隔 86 秒、190 秒陆续进来，被「10 分钟内不重复花钱」的闸挡住了（§7）。
我看着这四次，脱口而出：**「你连点了四下。」**

她说：「我怎么记得我只点了一下。」

**她是对的。后面三次是 app 自己发的。**

进这一页（`onAppear`）、以及每次切回前台（`scenePhase == .active`），
都会跑一个「自动接上一轮」——这个设计本身是对的，是为了修更早的一个坑：
她中途退出界面，钱已经花了，服务器还在跑，回来时屏幕却一片空白。
坏在**它跟人按的那一下走同一条路**，于是有了两个都会花钱的洞：

**① 拦它的那个标志位，视图一重建就复位了。**
`if !checking` 里的 `checking` 是界面状态（SwiftUI 的 `@State`），
视图重建时它归零，而在途的请求还活着 —— 于是「还在跑」这件事，
在拦截逻辑眼里变成了「没在跑」。同一个坑我们在同一个文件里踩过两次。
**要拦「视图重建了但活儿还在跑」，就不能用一个跟着视图一起重建的东西去拦。**

**② 两个超时一样长，边界必然漏。**
客户端的「在途记号」600 秒，服务端的「结果缓存」也是 600 秒。
记号第 599 秒自动接上去，服务端缓存第 601 秒刚过期 ——
**于是一次没有任何人按过的请求，真打五发、真花钱。**
这次没漏是运气。两个互相兜底的窗口，短的那个必须明显短，不能相等。

修法有三层，最外面那层才是根治的：

```js
// 服务端：自动接的那一路带 restore:true。
// 走到这一步说明缓存已经没了 —— 空手回去，别打。
if (restore === true) {
  return reply.send({ ok: false, restore_miss: true,
    error: "上一轮的结果已经过期了（没接上）—— 这次一发都没打，没花钱。" });
}
```

> **一个会花钱的接口，必须能分辨「这一发是人按的吗」。**
> 分辨不了的时候，默认答案是「不是」，然后什么都别打。

配套还要注意：自动接空手回来时，**别拿那个空响应去盖掉屏幕上已有的报告** ——
那份是用户真花钱买来的，比一个 `ok:false` 值钱得多。

顺带修掉同一次翻出来的两条显示层的错：

- **复用的那次不报账。** 那行原来是二选一：`reused ? "这次没再打模型" : "打了 N 发花了 $X"`。
  可复用的响应是把上一次的 payload **原样展开**再发的，钱一直在里面，是渲染丢的。
  **「这个请求没花钱」被印成了「这次体检没花钱」，这是两件事。**
- **两种状态共用一个布尔。** 「10 分钟内复用旧账」（真没花钱）和
  「同一轮还在跑、把你挂上去等」（**那一轮正在花钱**）都标成 `reused: true`，
  后者于是被印成「复用了上一次的结果」——一句在事实层面就是错的话。
  状态比标志位多的时候，多出来的那种一定会借别人的文案说话。

但这一条真正的教训不在代码里：

> **别把日志里的请求数，当成人的动作数。**

四次请求摆在眼前，最省事的解释是「他点了四下」，而且它看起来完全说得通。
是她说了一句「我记得我只点了一下」，才有人回去看那条自动路径。
**这跟 §2 是同一个病的另一副面孔**：那边是把「没测出来」说成「测出来是坏的」，
这边是把「我不知道谁发的」说成「用户发的」——
都是拿一个手边现成的解释，去填一个本该标着「不知道」的格子。

（这个仓库里的命令行版没有那道复用缓存、也没有界面，所以这一条在
`tool/cache-check.js` 里不存在。写在这儿是因为**谁做「自动重试 / 自动接回来」都会踩** ——
见 §7：那一节整节讲的就是跟中转站无关、做按钮本身的坑。）

### 第 26 条：`stop_reason=max_tokens` 被判成「不会调工具」🟢

2026-08-17 她截图：「这里说不能调用工具，**但是我调用了可以的**。」

界面上写着「不会调 · 强制(tool_choice:any)」，红字建议「缓存再省也没用，换通道」。
而小字里躺着真正的证据：

```
一个工具都没调，stop=max_tokens
```

**`max_tokens` 的意思是话没说完。**那条通道的模型名里带 `thinking`，
中转站会自动开扩展思考 —— 思考先把 1024 token 吃光，**根本没轮到吐 `tool_use`**。
探针测的其实是「它能不能在 1024 token 内想完」，而不是「它会不会调工具」。

两处都要改，缺一不可：

```js
// ① 给思考留够地方，否则这一发从一开始就测不出东西
model: _model, max_tokens: 4096, stream: true,

// ② 「被截断」是独立的一档，不是「不会」
const _cut = !_tool && _stop === "max_tokens";
verdict: _tool ? "会调"
       : (_cut ? "没测出来（它想太久，token 用完了）"
       : (_forced ? "不会调" : "这轮没调（非强制，不算数）")),
ok: _tool ? true : (_cut ? null : (_forced ? false : null)),
```

这是 §2 那一族的第 N 次复发，但**这次的代价最贵**：前几次是把「不知道」说成坏消息，
顶多让人多查一会儿；这一次它会**劝人换掉一条真正能用的通道** ——
而那条通道在真实对话里天天在调工具。

> **一个诊断工具最危险的时刻，不是它报错，是它自信地给出一个可执行的错建议。**

🔴 **顺序值得记一笔，因为它跟第 24 条正好相反。**
第 24 条里，是这个仓库的命令行版**先**修好、我们自己天天用的按钮后修，
当时的教训是「把东西抠出来给别人看，比自己盯着它看更容易发现问题」。
这一次反过来了：**用的人先撞见了自家那份，而开源这份带着同一个 bug 在外面跑了两天。**
两个方向都发生过，说明真正起作用的从来不是「抠出来」这个动作本身，
而是**有没有人真的在用它、并且会说出那句「但是我调用了可以的」**。

### 第 27～30 条：一句「这咋非流式 -10% 去了」，一次牵出四条 🟢

2026-08-29 凌晨，她截图问：**「这咋非流式 -10% 去了？」**
那一屏上，非流式这栏写着「命中」，紧跟着「省 **-10%**」。

命中了，却省出一个负数。

#### 第 27 条：有的站子的 `input_tokens` 已经含着 `cache_read` 🟢

真凶就摆在同一张卡的小字里：

```
第一发 in=21860 w=0 r=0     ← 冷启，没命中
第二发 in=21860 w=0 r=21523 ← 命中了
```

**两发发的是同一段前缀。**按 Anthropic 官方口径，`input_tokens` 和
`cache_read_input_tokens` 是**不重叠**的两栏，命中之后第二发的 `in`
应该只剩没命中的那几百。它却一个字都没少 —— 说明这条站子的 `in` ⊇ `r`。

而折算「等价全价 token」的公式（§3.3 里那条）又把 `r` 加了第二遍：

```js
const _units = (x) => (x.in || 0) + (x.w || 0) * 1.25 + (x.r || 0) * 0.1;
// 冷：21860
// 热：21860 + 21523 × 0.1 = 24012      ← r 被算了两次
// 省 = 1 - 24012 / 21860 = -10%
```

**命中越多，这个数越负。**一条缓存工作得越好的通道，这个按钮越会说它坏。

同一个双算还印出了另一个数字：「打中 **43383** token」（21860 + 21523）。
**两发发一样的东西，token 却翻倍** —— 这个自相矛盾就摆在界面上，
而按钮自己一个字都没说。**能自检的矛盾没有自检，等于把矛盾交给用的人去发现。**

判据要两条同时成立，不能只看「in 比 r 大」：

```js
// ① 这一发确实命中了；② 命中之后 in 几乎没缩水（≥ 冷启的 95%）
const _inclusive = !_blind && (_b.r || 0) > 0 && (_b.in || 0) >= (_b.r || 0)
                   && (_a.in || 0) > 0 && (_b.in || 0) >= (_a.in || 0) * 0.95;

const _units = (x) => (_inclusive
    ? Math.max(0, (x.in || 0) - (x.r || 0)) + (x.r || 0) * 0.1
    : (x.in || 0) + (x.r || 0) * 0.1) + (x.w || 0) * 1.25;
```

修完拿同一组真数字重算：**省 89%**，和账单差值算出来的 86% 终于对上了。
「打中」那栏也回到 21860，跟「没打中」一样 —— 同样的前缀，本来就该一样。

> 缓存写那一档（`cache_creation_input_tokens`）**没法用同样的办法验**：
> 这两发的 `w` 都是 0，没有样本。所以它照旧全额算 —— **宁可高估自己的成本。**

#### 第 28 条：「看不见」被印成了「没命中」🟢

同一张卡的上半截，流式那栏：

```
流式  没命中
没打中 15007 token · $8.9580   打中 15007 token · $1.2277   省 0%
第一发 in=15007 w=0 r=0 ｜ 第二发 in=15007 w=0 r=0
```

缓存两栏全是 0，判成「没命中」。**可同一次的账单差值是 -86%。**

钱省了就是命中了。这条站子只是**在流式这条链路上不返回缓存字段**（§1 讲过
流式/非流式是两条独立的转发链路，这里是同一件事的另一个侧面）。

原来那个「瞎」的判据只认一种长相：

```js
const _blind = (_b.r === null && _b.w === null) ||
               ((_b.in || 0) === 0 && !(_b.w || 0) && !(_b.r || 0));
```

`in` 有数、只有缓存两栏是 0 的这种，它认不出来。补一档：

```js
const _silentHit = !_blind && !_hit && !(_a.w || 0) && !(_b.w || 0)
                   && _savedBill != null && _savedBill >= 30;
// verdict: … : (_silentHit ? "看不见（缓存栏全 0，但账单降了）" : "没命中")
```

这条是 §2 那一族里**最贵的一种**：它不是把「不知道」说成坏消息，
而是把「看不见」说成了一个**可执行的坏消息** —— 照着它去关掉流式，
真实请求那边会连思考链一起丢掉（§8.1 那条建议差点就是这么反过来的）。

#### 第 29 条：用一个没验证的解释，去解释一个没验证的数字 🟢

**这一条我写错过一次。错法比 bug 本身有用，所以写全过程。**

##### 现象

卡片上那一栏：

```
没打中 15007 token · $8.9580     打中 15007 token · $1.2277
```

折一下：$8.958 ÷ 15007 × 10⁶ = **每百万 token 约 $597**。
正牌最贵的型号也就 $15 上下 —— 差两个数量级。

##### 我的第一版结论（错的）

> 「账单计数器是**账号级**的。体检那两分钟里，同一个账号上还有别的请求在跑，
> 钱全记在同一格。数字是真的，只是不该摆在『没打中／打中』旁边。」

听起来很顺。它还能引用本文 §3.3「账单不能做分母」——**那一条是真的**，
是真踩出来的（「省 -575%」那次，冷启的钱被异步入账劈成了两半）。

我把这段写进了卡片，也写进了这份文档。

##### 用的人一句话把它戳穿

> 「但是今天测的时候就只有探针等支出，没有算错，那这也是 bug 吗？」

去查网关日志：体检窗口 **16:57:17 → 16:59:44**，那两分半里打过模型的请求：**零**。
（窗口内只有本地接口；最近一次真实对话请求 16:55:42 发起、16:55:58 结束，在窗口外。）

**ta 是对的。那笔钱一分不差就是 7 发探针花的。**

##### 那真正的毛病在哪

```js
const _money = (c) => c == null ? null : "$" + (c / 100).toFixed(4);
```

站子回的是 `{"total_usage": 6592.224}` —— **一个没有量纲的数字**。
它长得像 OpenAI 的 billing 接口，于是我们默认「单位是美分」，除以 100，加个 `$`。
**这两步都没有依据。**

验它只要一发：`input 434 + output 13` → 账单涨 **19.96**。
把这个数拿给账号的主人看，ta 一眼就说出了那一发实际花了多少 ——
跟我们印在卡片上的**差了将近一个量级**。

除以 100（子单位 → 主单位）那一步**是对的**；错的是我们凭"它长得像 OpenAI"
就替读者认定了**币种**。

反推那次体检：3134.38 个单位，按单发实测的比例折回去 ≈ **7.8 万等效 token**，
而 7 发探针本来就是这个量级（21860 + 337 + 15007 + 15007 + 24875 ≈ 77k）。
**账目从头到尾是平的。数值一直对，错的只有那个符号。**

（用同一发还能顺手量出这条通道相对官方牌价的溢价 —— 这个数字有用，
而「每百万 token $597」是拿一个错的币种算出来的，只会吓人。
**具体倍率跟着你自己的站走，这里不替你填。**）

##### 🔴 为什么这个 bug 能活这么久

账号的主人后来说了一句，我觉得该原样放进来：

> 「一般中转站充钱的时候大家都知道是什么倍率和单位的呀。」

**对。对用中转站的人来说，单位不是知识，是常识。**
正因为是常识，**没有人会想到去检查工具有没有把它假设错** ——
每个人看见 `$31.34` 都会在心里自动换算成自己那套，然后觉得一切正常。

所以这一条不是写给"用中转站的人"的（对他们，讲单位是把常识当发现）。
它写给**要自己做一个这种按钮的人**：

> **你知道你的站是什么单位。但你写的代码会被别人跑。**
> 别把你自己的常识写死进去 —— 报原始数字，让读它的人用自己的常识去读。

##### 这一条真正的教训

前面 §2 讲的是「别把没测出来说成测出来是坏的」。这一条比那更深一层：

> **我用一个没验证的解释，去解释一个没验证的数字。**

`$597/M` 是从一个我没验过的单位算出来的；「账单被并行请求污染」我也没去日志里查过。
两边都是猜，拼在一起却得到一个**读起来毫无破绽的因果**。

它有毒的地方在于：**它引用了一条真规律给自己背书**（账单确实是账号级的、
确实被污染过，§3.3 有真证据），只是那条规律这次没有发生。

**用真规律解释假现象，比直接编还难被发现 —— 因为每一句拆开看都是对的。**

戳破它的两句话，都不是我算出来的：
一句「可是那会儿没有别的支出」定了性，一句报出实际花费定了量。

> 诊断工具的作者最该防的不是算错，是**给出一个自己没验证、但听起来很懂的解释**。
> 遇到离谱的数字，第一件事是**验单位**，不是想原因。
>
> 而验单位往往一句「你充值的时候是什么比例」就够了 ——
> **有些事实不在日志里，在用的人脑子里。开口问比推理便宜。**

第 27 条修完，顺手 grep 了一遍同样的形状，在真实用量那块找到第二处：

一模一样的加法。**现在看不出来，因为那条通道真实轮次的 `cr` 全是 0** ——

## 9. 我们没做 / 没验的

- ⚪️ 端点清单形式只跑通了**一次**真链路 + 3/3 的行为 A/B。**样本太小，不敢说稳。**
  已做成开关，默认关，出问题一秒切回。
- ⚪️ 端点清单形式下，写入类工具（`add_*` / `save_*`）拼错参数的实际概率未知。

  比「只搬只读工具」这种折中好 —— 因为写入类占工具块的 **58%**，
  只搬一半等于把大头留在原地，收益砍半而风险一点没减。
  **用范围换安全是最贵的那种保守。**
- ⚪️ 拆块（§1.3）改完之后还没在一条**真会缓存**的通道上验过收益。
- 🟡 「某些通道在做账号池负载均衡」是从 `8871 + 1517 = 10388` 这个算式倒推的，
  没有站方确认。
- 🟢 **四个显式缓存断点的槽位我们已经占满了**（人格 / 摘要 / 工具块末尾 / 倒数第二条历史），

  [延伸阅读](#延伸阅读)里那篇 postmortem 的「修复前」一样。
  **量过之后是小钱**（近 14 天 1085 条回复只有 63 条走到第二轮，丢的只是断点之后那条尾巴），
  所以**没改**。写在这儿是因为结构风险真实存在，不是因为量出了损失。

### 第 31 条：第 26 条的药方不够猛，而且**永远不可能够猛**

2026-09-02，同一位读者又发来一张几乎一样的截图——距 §26 修好整整半个月，
「调用工具」那一档还是「没测出来（它想太久，token 用完了）」。

**第一反应是老办法：再加钱。** §26 把 `max_tokens` 从 1024 提到 4096；
这次直接顶到 16000——四倍于上次的药量。**结果一模一样**：这条通道这个
"thinking" 模型，四发里有一发照样能把 16000 token 全部花在思考上，
一个字的 `tool_use` 都不吐，`stop_reason` 照样是 `max_tokens`。

```
max_tokens: 4096  → 仍被截断
max_tokens: 16000 → 仍被截断（四倍预算，同一个结局）
```

**这才看明白 §26 那次治标不治本。** 强制 `tool_choice:any` 之后，这个模型的思考
preamble 没有一个天然的收敛点——它不是"需要更多空间"，是**根本没打算停**。
再加多少预算都只是把"多久之后截断"往后推，永远推不到"它自己说完了"那一刻。
**只要测试方法是"逼它一定要在预算内做完一件事"，对这一类模型就永远会撞到同一堵墙。**

真正管用的不是加钱，是**换一个完全不需要它配合的证据源**：

```js
// 强测没测出来 / 判定不会调时，去查真实对话记录——
// 真实调用是免费的、已经发生的事实，比任何一次新的强测都硬。
function _realToolEvidence() {
  // 复用 §6 的 --usage-file：给每行加一个可选的 tool_used 字段，
  // 命中同一条"站+模型+端点清单+流式"通道就计一次。
  ...
}
if (_tools.ok !== true) {
  const hits = _realToolEvidence();
  if (hits > 0) _tools.detail += `　—— 但真实记录里已经成功调用过 ${hits} 次，这条通道没问题。`;
}
```

**配套一个自己刚犯的错**：加了这条证据之后，只补进了 `detail` 那一行文字，
上层「该怎么选」的建议栏压根没读它——于是屏幕上同时出现"调用过 N 次"和
"建议换通道"，同一份体检自己打自己脸。§4（覆盖式赋值顶掉结论）和这次是
同一个形状的另一次发作：**加一条新证据，要检查它有没有传到*所有*引用旧结论的地方**，
不能只改第一个读到它的分支。

**顺手核实的一件事，省得以后有人重新怀疑**：`msg_01` 这个"看着像正牌"的前缀
判据会不会也过时了？拿一条**当下**、**确认无疑**是官方直连的响应去对——
现在（2026-09）的真实 id 依然是 `msg_01` 开头。这条判据没有过期，
只是大多数中转站的 id 形状本来就不是这一种，"认不出"是诚实的默认结果，
不是判据坏了。

> **一个诊断方法测不出结论，不代表事实测不出——先想想有没有别的证据源，
> 别下意识地就去加大同一个旋钮。**

相关病灶：§2（把「没测出来」当坏消息）、§4（覆盖式赋值顶掉结论）。

讲「写进去了，却永远命不中」：`tool_result` 明明有 `cache_creation_input_tokens`，
下一轮却读不回来。两层根因，我们读之前都不知道：

1. **Anthropic 最多只认四个显式缓存断点。** 四个槽位被人格 / 日记 / 摘要 / 滚动历史占满，
   `tool_result` 一个都排不上。
2. 给「只含工具结果」那条消息补断点时，实现里注入了一句说明文本，
   而那句话只存在于当次请求的副本里，下一轮重建时消失 → 前缀不匹配。

修法：把摘要那个断点让给 `tool_result`（5 分钟 TTL），
`cache_control` 直接挂在已有的 `tool_result` 块上、不新建文本块，
并确保中间那层换格式的时候不要把这些标记吞掉。最终布局按稳定性递减：
人格(1h) → 日记(1h) → 滚动历史(1h) → 工具结果(5min)。

**读完我们照着自查了一遍，两条结果记在这儿：**

- 我们的四个槽位同样是满的（人格 / 摘要 / 工具块末尾 / 倒数第二条历史），
  `tool_result` 同样排不上。不过我们的断点打在「倒数第二条历史」，
  多轮工具调用时新追加的块落在断点之后，丢的只是那条尾巴，
  近 14 天 1085 条回复里也只有 63 条走到第二轮 —— 对我们是小钱，所以没改。🟢
- 第二层那个坑我们恰好躲过了：每轮必变的实时状态早就挪进了最后一条用户消息，
  也就是断点之后（见 §1.3）。当时是为别的原因挪的，读完这篇才知道顺带避开了什么。🟢

这一节的思路来自 🍬 老师这篇文章，我们只是拿它当清单自查了一遍。
